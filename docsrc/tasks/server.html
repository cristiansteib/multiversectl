See and run the whole setup in a page

$ multiversectl server start --open
✓ serving http://127.0.0.1:7777/?t=… in the background (pid 4242; it can start, stop, create and remove universes); stop it with: multiversectl server stop
$ multiversectl server status
$ multiversectl server stop

start runs the web view detached from your terminal and remembers it, so closing the shell does not stop it; start again reports the one already running, and stop ends it. Its output goes to server.log beside the configuration file, which is where start shows the reason when the server cannot start, such as a port already in use. To keep it in a terminal instead, run multiversectl-server itself; Ctrl-C stops it.

multiversectl server restart stops it and starts it again with the address and flags it had, and the link stays the same. An update replaces the program on disk but not the one already running, so self-update restarts a running web view for you, the install script does too, and after a package upgrade (brew upgrade, .deb) server status and status say it is still running the older build. restart --if-running does nothing when there is no server, for scripts.

multiversectl-server is a separate program from multiversectl, built from the same project: the command line carries no web server, and multiversectl server only starts and stops that program, which it looks for beside itself and then on the PATH.

The page is live: the server watches the machine and pushes what changes over a websocket, so a universe you start from a terminal appears on the page without a click, and the indicator in the corner says live while the connection is up. If the connection drops, the page asks again every ten seconds until it is back.

  • Overview: the root catalog, the projects installed here, and where each has drifted, as project status shows it. Fetch remotes and compare is --fetch. A stale project has an Update button, and any other a Make current button.
  • Catalog: the tree, each node with its kind (root, catalog or project) and where it lives, with the platform's mark and the notation github:owner/repo, and the file when two catalogs share a repository. What is installed is marked and layers you cannot reach are listed with the reason. Filter it by name, path or repository, and copy the install command for any project.
  • Fleet: every universe of every installed project, with its branches, its apps and the state of each service, its addresses as links, and the paths of its checkouts. Press / to filter. Doctor runs the checks for a project or a single universe.
  • System: the version of the server, of the command line beside it, and of git, docker, docker compose, gh and glab with where each was found, the latest release and whether you are behind it, and the file format.

Each project also has a page with its repositories, whether each is cloned, its apps and their hostnames, and the proxy entrypoints it needs.

Act from the page

A project has New universe, Update and Make current. New universe has the two modes of the command line: a fresh branch (the next free number is filled in, with the numbers it skipped and why, and an optional base and branch name) or an existing one (chosen from the branches there are, with the repositories that have each shown, and the option to leave the others on their base). A universe has Start, Stop, Remove… and, when its code is behind the branch it follows, Update code (universe sync); the card and each repository show how many commits behind, and the repositories table of a project does the same for the shared clones. Each is the use case the command line runs, started in the background; what it prints, including what docker compose prints, streams into the panel at the bottom as it happens, and the panel keeps the last thirty. A universe has one operation at a time, because two would be two compose commands fighting over one project; different universes run side by side.

Removing is the one that cannot be undone, so it is slower on purpose. The dialog asks for the universe's name to be typed, and the server checks it again. If a worktree has uncommitted work the server refuses and says where; only a second press, now labelled Remove anyway, discards it. --read-only removes every button and makes the server refuse every action.

Let a coding agent work with it

An agent needs no server and no protocol: it runs the command line, and -o json gives it what it needs in few tokens. Each universe is its own folder and its own set of containers, so several agents can each work in one at the same time.

$ multiversectl universe ls -o json
{"project":{"name":"acme","root":"/home/me/acme","manifest":"…/multiverse.yaml","universesDir":"…/universes","clones":{"api":"…/api"}},
 "universes":[{"name":"3","state":"running","up":"3/3","dir":"…/universes/3",
   "checkout":{"api":"…/universes/3/api"},"branch":{"api":"u3"},"urls":["https://api-3.example.test"]}]}

The output is one line with no indentation, and only what an agent acts on: where the project and its clones are, and for each universe whether it runs, the folder of every repository (where to edit), the branches and the addresses. A healthy universe adds nothing more; one with services that should be up and are not lists them under down. universe ls 3 -o json shows only universe 3 and universe status -o json gives the same view. --json is the same as -o json on any listing, and works on every command: --help --json prints the command, its flags, examples and subcommands as one document (multiversectl --help --json is the whole tree), and a command that only acts, such as universe up, prints its messages and tables as one JSON object per line ({"level":"ok","message":"…"}), with a failure as {"level":"error",…} on standard error. -o json,wide is everything: services and their state, volumes, compose project names and times.

A typical session: universe new, universe up, then universe ls <name> -o json for the folders and addresses, edit in checkout, and universe rm when done. project status -o json and status -o json say what has drifted. Starting, stopping or removing a universe holds only that universe, so agents on different ones do not wait for each other; creating takes the next number and new branches, so creations take turns.

Who can use it

A page that can remove a universe must not be open to whoever can reach the port, so the server makes up a token the first time it starts, keeps it in server.token beside the configuration (readable by you only), and serves nothing without it. The token is kept so that a restart does not end the link; delete the file and restart to change it. The link start, status and --open print carries the token; opening it trades it for a cookie and redirects to an address without it, so it does not stay in the address bar or the history. The cookie is HttpOnly and SameSite=Strict, which stops a page on another site from using it. Without the cookie every request is refused, including the websocket, with a page that says how to get the link again.

On top of that the server listens on the loopback address only and answers only requests addressed to localhost, 127.0.0.1 or ::1; without that second check a web page on another site could point a name it controls at your machine and talk to it through the browser. Anything that changes state also needs a header only the page's own script sends, and a request from another origin is refused, the websocket included. --addr picks another loopback port (0 chooses a free one). --expose allows any address and any host name; the token still applies, so it is the way to reach the page from another device, and the link is then the password: it is in server.log and in the file status reads, both readable by you only.

The page loads nothing from outside, which its content security policy enforces, and builds everything from text, so a branch name or a note cannot inject markup.

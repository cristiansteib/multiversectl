Use a project someone points you at

$ multiversectl catalog install acme/multiverse
$ multiversectl universe new 1
$ multiversectl universe up 1

That is all, on a machine with nothing set up: no catalog, no prompts. The source can be owner/repo (GitHub), any git URL, or a path. A repository that holds a catalog.yaml is read as one; one with only a multiverse.yaml is read as a workspace. install says which it took the source for.

Keep your own index

# looks for your root on GitHub and GitLab, or asks: a new private repository, one you have, or only here
$ multiversectl init
# or say it
$ multiversectl init --create multiverse-index
$ multiversectl init me/multiverse-index
$ multiversectl init --local ~/multiverse-index

--create uses the GitHub CLI and makes the repository private; --public is the only way to make it public. Without gh, make the repository yourself and pass it. A repository that already holds a catalog.yaml is used as it is, and one that does not gets one. Creating a repository and pushing both ask first; --yes accepts them for scripts. A root that is only on this machine is fine to start with, and status keeps reminding you that nobody else can use it.

On a machine that has nothing, init first searches the services you are signed in to for a repository tagged as a root (the topic multiversectl-root) and offers what it finds at the top of the list. On a machine that is already set up it says so, with the root and what is installed from it, and offers to keep it; it checks the root is marked as a CatalogRoot and tags its repository, which also upgrades a root made before the kind existed.

To start again from another root, init refuses while workspaces installed from the current one exist, because they would point into a root that is no longer used. multiversectl reset forgets the root and the installed workspaces, deleting no file, checkout or universe; run system --prune first if you want the universes gone.

Start again on a new machine

$ gh auth login                      # or let init sign you in
$ multiversectl init                  # finds your root
$ multiversectl catalog install        # pick the projects this machine needs
$ multiversectl universe new 1

That restores what git holds: which projects exist, how each is described, and every repository. It does not restore what git does not: files a project keeps out of it (.env, service-account keys, which a project lists under secrets and which are copied from its clones), uncommitted work and branches that were never pushed, database volumes, and universes, which are created again. Put those somewhere of your own before wiping a machine, and keep a project's full manifest in its repository rather than beside it.

Put a project in the right place

$ multiversectl catalog add acme/billing
› acme/billing holds a workspace manifest (billing)
┃ Where should it go?
┃   index (root)         writes to github:me/multiverse-index
┃   ├─ personal          writes to github:me/multiverse-index
┃   └─ acme              writes to github:acme/index · another repository
┃ ❯    ├─ backend        writes to github:acme/index · another repository
┃      └─ frontend       writes to github:acme/index · another repository
┃      secret-team       no access or not found: github:acme/secret-index
↑ up • ↓ down • / filter • enter submit

Questions are asked with a list you move through: ↑ ↓ to move, Space to tick when several can be chosen, / to filter a long list, Enter to accept and Esc or Ctrl+C to stop. A command that is missing something it needs asks for it this way, instead of failing: universe up offers your universes, catalog rm offers the entries of the tree, catalog use your installed workspaces, universe new the next free number. Without a terminal, such as in a script, nothing is asked and the command says what it needs.

The default is the deepest catalog kept in a repository owned by the same owner as the project, since that is usually where it belongs; otherwise the root. The name is asked only when it is already taken there, and listing a project that is already somewhere else in the tree asks first. --at <path> names the place (/ is the root), and with --yes and no --at an entry goes in the root, never into a repository nobody named.

The source can be a repository, a path to a local checkout (added by its origin, because other machines have to be able to fetch it), or a manifest file. A manifest file has no repository, so it goes into one: a copy in the catalog's own, or a repository of its own, which makes a project.

$ multiversectl catalog add ./acme.yaml --new-repo acme-org/multiverse

Writes go to the file that owns the place you chose, are committed, and, in a remote repository, are pushed after you confirm once, before anything is written. Only that repository is fetched first. If the push is rejected the command says so and leaves your copy clean. catalog create <name> makes an empty catalog to group projects under, and catalog rm <path> takes an entry out; what it pointed at is untouched.

Install what this machine needs

# a workspace, or everything under a catalog
$ multiversectl catalog install acme/backend/billing
$ multiversectl catalog install acme personal/notes
# no source: pick from your catalog, installed ones are marked
$ multiversectl catalog install
$ multiversectl catalog status
$ multiversectl catalog use billing

A workspace goes in ~/multiverse/<name> unless you say otherwise, and the install shows that folder, prefilled, so Enter accepts it or you type another; --root (the folder itself), --base (the folder it goes under), $MULTIVERSECTL_ROOT or --yes settle it without asking. Pointing --root at a folder that already holds the checkouts reuses them. The first workspace on a machine becomes the current one; later ones are installed beside it and say so. A source is read in a fixed order: a node in your catalog, then a path, then a git URL, then owner/repo.

Keep installed workspaces current

$ multiversectl catalog status --fetch
WORKSPACE  FROM            STATE
* acme      acme/multiverse  manifest behind 1 · billing-api not cloned
› next: multiversectl catalog update acme
$ multiversectl catalog update
✓ billing-api: cloned
✓ acme: manifest moved forward 1 · billing-api cloned

status compares each workspace with where it was installed from, offline unless you pass --fetch. update fetches, moves each manifest forward, and clones the repositories the new manifest lists. It refuses a manifest with local changes and leaves a pinned one (a tag or commit) alone. uninstall <name> forgets a workspace and leaves its files.

Make a project others can join

# in an empty directory, or a checkout of a repository you made for it
$ multiversectl project init

The guide asks, in turn, and shows the plan before it creates or pushes anything:

  • Its repositories. The git checkouts already beside the directory (each one's origin becomes its URL), a search through your repositories on GitHub or GitLab (pick the account or organization, filter by name, tick the ones you want), or URLs you paste: git@..., https://... or owner/repo. Mix them as you like.
  • Its name. What most repository names start with (acme-api, acme-ui are acme), which also shortens their keys to api and ui.
  • Where its own repository lives. A new private one under any account or organization you can create in, on GitHub or GitLab; one that exists; the directory's own origin; or only on this machine for now.
  • Where to list it in your root catalog, with the same picker as catalog add, and whether to install it here so the next command can be universe new 1.

It writes multiverse.yaml, catalog.yaml and a short AGENTS.md into the directory, commits them and pushes. The AGENTS.md tells a person or a coding agent what the repository is, lists its repositories, and gives the commands to install the project and run universes, with the few rules for keeping it shareable; one that is already there is kept as it is. A repository with a docker-compose.yml becomes an app of the same name; one that was found cloned and has none is marked runtime: none; one only chosen from a search is left to start as an app when it gets a compose file. GitHub needs gh and GitLab needs glab installed; if you are not signed in, choosing the service signs you in first, with the tool's own browser login, and the guide carries on afterwards. Slow steps (listing repositories, creating one, pushing) show a spinner. Any other host works by URL. Every answer has a flag, so with enough of them it asks nothing:

$ multiversectl project init ~/acme/multiverse --scan --create acme-org/multiverse --yes
$ multiversectl project init --name acme --repo acme-org/api --repo https://gitlab.com/acme/web.git --local

What it makes is a repository that is both the project's index and its own workspace definition. The catalog lists that workspace with no repo, because a reference stays in the repository it is written in, and can link deeper catalogs when the project needs them.

# catalog.yaml in acme-org/multiverse
apiVersion: multiverse/v1alpha1
kind: Catalog
metadata:
  name: acme
spec:
  workspaces:
    - name: acme
      source: {path: multiverse.yaml}   # this repository's own manifest

Anyone then needs multiversectl catalog install acme-org/multiverse. To do it by hand instead, write those two files yourself. If they keep an index of their own, install suggests catalog add for it. Drop machine-specific lines such as an absolute spec.root from a manifest you share: install chooses where it goes.

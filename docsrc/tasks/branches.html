Work on two branches at once

# a new universe: branches of its own, named after it
$ multiversectl universe new fix/login --note "PR 412 review"
$ multiversectl universe up fix/login
$ multiversectl universe urls fix/login
http://api-fix-login.10-0-0-5.traefik.me
# or number it (leave the number out for the next free one), and say where it starts
$ multiversectl universe new 2 --branch feat/invoicing --base api=release/1.2

A new universe never reuses a branch: if the name is taken in any repository, in the clone or on origin, nothing is created and every clash is listed. A numbered one takes its branch from spec.branch, u{{universe}} by default. Every command accepts the name as typed, the directory it lives in, or the slug in its hostnames. Each universe has its own containers, volumes and hostnames, so the two run side by side.

Review or continue a branch that already exists

$ multiversectl universe checkout fix/login           # or with no branch, to pick from the ones there are
$ multiversectl universe checkout fix/login --only-existing

This is the other way in: instead of starting branches, it checks out the one you name, in every repository that has it. A repository that lacks it gets a new branch of that name, or with --only-existing stays on its base, detached. It refuses a branch that is checked out in another universe or in the shared clone, because git allows a branch in one worktree only, and it refuses a name no repository has, so a typo does not become a branch. When you remove the universe the branch stays; only a branch a universe started is ever deleted.

Add a repository to a workspace

# multiverse.yaml
spec:
  repos:
    - name: worker
      url: git@github.com:acme/worker.git

That is the whole change: a repository no apps entry names gets an app of its own name, its compose files are found by convention, every service they define is started and the addresses come from their labels. Add an apps entry only to change one of those, or to split the repository into several apps.

# clone the new repo (already-cloned ones are skipped)
$ multiversectl catalog install ./multiverse.yaml --root ~/acme
# add its worktree to an existing universe; existing checkouts are kept
$ multiversectl universe new 3
$ multiversectl universe up 3 worker

For a repository you only edit, with nothing to run, use runtime: none.

Remove a universe and its data

$ multiversectl universe rm 3
# skip the prompt
$ multiversectl universe rm 3 --yes

rm lists what it will destroy and asks you to type the number back, which is the one question that is deliberately not a list to move through. It removes:

  • the universe's worktrees (uncommitted work in them is lost);
  • its containers and volumes, so every database in it;
  • its directory and state file.

The shared clones are not touched. To stop a universe and keep everything, use multiversectl universe down 3.

Clear out every universe on the machine

$ multiversectl system                    # what each workspace holds
$ multiversectl system --prune            # remove the idle ones, asking first
$ multiversectl system --prune --all --yes # everything, running ones included, no question

--prune does to each universe what universe rm does, in every installed workspace, or only the one you name with -w: the containers and volumes, the worktrees, the directory and the state file. It is deliberately not a way to stop containers and keep the data; that is universe down.

Two kinds of universe are kept unless you say otherwise, and each is listed with the reason:

  • one with containers running, until you add --all;
  • one with uncommitted work in a worktree, until you add --force. --yes only skips the question; it never discards work.

What it does not touch: the shared clones; the shared proxy; and the installed workspaces and catalogs. The branches a universe started are deleted only when every commit on them is already on the base branch or on a remote, so committed work is never lost, and one holding anything else is kept and named.

What a catalog is for

A workspace manifest describes one project. A catalog answers a different question: which projects exist, and which of them should be on this machine. It is a file of pointers, so the manifests stay with the repositories they describe and nobody has to copy them.

Catalogs nest. A personal catalog can link a catalog that a team keeps in its own repository, which can link another, and each layer is edited by whoever owns that repository. A machine installs only the branches of the tree it wants.

You do not need one to use a project. multiversectl catalog install acme/multiverse works on a machine with no catalog at all; the catalog is for keeping your own index of what you work on.

Catalog, CatalogRef and WorkspaceRef

apiVersion: multiverse/v1alpha1
kind: Catalog
metadata:
  name: me
spec:
  catalogs:                         # CatalogRef: descend into another Catalog
    - name: acme
      source: {repo: git@example.test:acme/multiverse-index.git, ref: main}
    - name: personal                # no repo: a file in this same repository
      source: {path: catalogs/personal.yaml}
  workspaces:                       # WorkspaceRef: a leaf
    - name: notes
      source: {repo: git@example.test:me/notes-workspace.git}
FieldMeaning
source.repoA git URL. Leave it out to mean the repository the reference is written in.
source.refBranch, tag or commit. Needs repo. A tag or commit makes that layer read-only.
source.pathRelative to the repository root, and it cannot leave it. Defaults to catalog.yaml or multiverse.yaml.

A node is addressed by the names that lead to it, for example acme/backend/billing. Names are unique among siblings. The schema is schema/catalog.v1alpha1.yaml.

The root, and how a new machine finds it

Every machine starts from one catalog, its root, and the root has its own kind so it can be told from the catalogs of the projects hanging under it:

apiVersion: multiverse/v1alpha1
kind: CatalogRoot
metadata:
  name: me

A CatalogRoot is a Catalog in every other respect: the same spec, and anything that reads catalogs reads it. One listed under another catalog is just a catalog there. What the kind adds is that init knows which one is the starting point.

On a hosting service the root's repository also carries the topic multiversectl-root. init sets it, and on a machine with nothing it searches your repositories, across your organizations too, for that topic, without cloning anything. A root made before the kind existed is a plain Catalog; init offers to mark it, which changes that one line.

Three separate things

  • The catalog is shared and versioned: what exists. It holds pointers, never definitions.
  • The workspace list is per machine, in ~/.config/multiversectl/config.yaml: what is installed here, which one is current, and where each came from.
  • Universes work as before. new, up, ls and the rest act on one workspace and never read a catalog.

Only install connects the first two, and it only reads: installing never writes to a catalog. catalog add, create and rm are the commands that edit one.

Names

A workspace is installed under its own name, billing, in ~/multiverse/billing. If that name is taken, the name above it goes in front (payments-billing) and then the next; --name overrides. The name does not change after install, so -w billing in a script keeps working if the catalog is reorganised. Anywhere a workspace name is accepted, the catalog path it was installed from is too: use acme/backend/billing.

Each installed workspace records where it came from, which is how status and update know it has drifted.

When a layer cannot be read

A layer you have no access to, or that has a bad file, shows as unavailable in multiversectl catalog, with the reason, and the rest of the tree still resolves. Cycles and chains deeper than eight levels are cut off the same way.

Several workspaces, one proxy

A machine has one proxy, and starting any workspace rewrites it from that workspace's manifest. Sharing its network and its default web port is therefore normal. What is not is a workspace that needs an entrypoint another one's proxy does not have, or a different network or bind address: starting the second reconfigures the proxy and the first loses it. install and doctor name those differences, by workspace name.

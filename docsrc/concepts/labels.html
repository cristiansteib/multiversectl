Why labels

A compose file already knows which port its service listens on and which settings depend on the environment. Writing that into a manifest means saying it twice and keeping the two in step by hand, so multiversectl reads the compose files instead — with docker compose config, so it sees the merged result, variables and profiles included.

Labels rather than a reference such as ${MULTIVERSE_ORIGINS} in the service's own environment:, because a compose file is also run by hand: the reference would resolve to nothing, while a label is inert metadata until multiversectl reads it.

Addresses: dev.multiversectl.host.*

The key names the host, the value is the container port:

services:
  app-dev:
    labels:
      dev.multiversectl.host.app: "4200"              # app-u3.<domain> → 4200
      dev.multiversectl.host.api: "8001"
      dev.multiversectl.host.api.entrypoint: devapi   # default: web
      dev.multiversectl.host.api.aliases: app,adm     # same service, more names
      dev.multiversectl.host.api.portForward: auto    # also at <ip>:<free port>
      dev.multiversectl.host.rpc.scheme: h2c          # a gRPC service
      dev.multiversectl.host.api.ready: /healthz      # up waits until this answers
      dev.multiversectl.host.rpc.probe: tcp          # doctor connects instead of asking over HTTP

By IP and port: portForward

Some clients refuse plain http to a hostname: an iPhone app's transport security allows an IP address but not api-u3.<domain>. dev.multiversectl.host.api.portForward: auto also publishes that service on a free host port, so it answers at http://<this machine's address>:<port> next to its hostname. The kernel picks the port once, it is kept in the universe's state (so the address you gave a phone survives restarts) and no other universe is given it. It is bound like the proxy: every interface with expose: lan, loopback only with expose: local. universe ls shows it as <host>:forward.

aliases is how one API answers under each front-end's own hostname on a second entrypoint, which makes a hard-coded :8001 work in every universe.

By IP alone: portForward: only

With auto a host answers under its hostname and at http://<ip>:<port>, and both are listed. only keeps the second: the host is reached at that address alone, and no address shown or handed to a service (<HOST>_URL, origins, the web view) is a name. For a service that should not be known by one, such as an identity provider whose issuer must be a single address. domain: none does it for every host.

A service that speaks gRPC: scheme

The proxy talks HTTP/1.1 to a service unless told otherwise, and a gRPC server answers that with an error the universe does not explain. dev.multiversectl.host.rpc.scheme: h2c has it speak HTTP/2 without TLS to that service (https is the other choice; http is the default). In a manifest it is scheme on the host.

Wait until it answers: ready

Compose calls a service up when its container runs, which can be long before anything answers: an initial build, a migration. After starting an app, up waits until every service that has a compose healthcheck is healthy, with a line for what it is waiting for. A host that sets dev.multiversectl.host.api.ready is polled as well: "true" asks its address until it answers with any status below 500 (the proxy's own "no route" 404 does not count), or connects to it for an h2c host; "tcp" only connects (a connection goes to the host's forwarded port; a host with none is asked over HTTP through the proxy instead, since the proxy accepts any connection whether or not a service is behind it); a path such as "/healthz" asks that path; "false", the default, does not wait. In a manifest it is ready on the host. The app's postUp hooks run after the wait, so they can rely on it.

The wait ends at --wait-timeout (5 minutes by default, for all of an app's services and hosts together). Running out of time is a warning naming what was waited for and the last thing it said, and the start goes on; --wait-strict makes it an error, and --no-wait skips the wait altogether.

How doctor checks it: probe

doctor asks each address of a running app over HTTP, and any answer below 500 proves the route and the service. A host that does not speak HTTP is checked the way it does: an h2c host is asked whether it accepts a TCP connection, and dev.multiversectl.host.rpc.probe (probe on a manifest host) says it outright: http, tcp, grpc or none to leave the host out. A connection that works is a success. The connection goes to the port the host is forwarded on (portForward); a host reached only through the proxy is asked over HTTP instead, where the proxy answers 502 to 504 when nothing is behind it, because the proxy itself accepts every connection. grpc is a TCP connection too: multiversectl carries no gRPC client, so the standard gRPC health check is not run, and the report says so.

With no labels at all

A service exposing exactly one port is reached at the app's own name, so the common case needs nothing. Anything ambiguous is an error naming the label to add, not a guess:

api: services "web" and "worker" both expose a port — label the one that
should answer: dev.multiversectl.host.api: "<port>"

Hosts declared in the manifest's hosts: win over labels, and exist for repositories you cannot change.

Ports: dev.multiversectl.publish

services:
  db:
    labels:
      dev.multiversectl.publish: "true"

Keeps this service's published host ports instead of dropping them. Only one universe can hold a host port at a time, so a service that asks for this is one only a single universe can run — usually worth it for a database you point a GUI at, rarely for anything else. The manifest's publish: list does the same from outside.

Values: dev.multiversectl.env.*

The key names an environment variable, the value names what to put in it:

services:
  web:
    labels:
      dev.multiversectl.env.DJANGO_ALLOWED_HOSTS: hosts
      dev.multiversectl.env.DJANGO_CSRF_TRUSTED_ORIGINS: origins
      dev.multiversectl.env.DJANGO_CORS_ALLOWED_ORIGINS: origins:space
      dev.multiversectl.env.API_BASE_URL: url:devapi
SourceValue
originsEvery address of the universe as an origin, each with its entrypoint's port, and the address by IP and port of every host that is forwarded (portForward), once its port is chosen. hosts stays hostnames only.
hostsEvery hostname, comma separated.
origins:space, hosts:spaceThe same list joined as the setting wants it: comma (the default), space, semicolon or newline. A framework decides the shape of its own setting, so it is named rather than guessed.
domainThe wildcard domain in use.
universeThe universe's name, as typed.
slugThe part its hostnames carry.
host:<key>One host key's hostname.
url:<key>One host key's whole address, port included.
forward:<key>The address of a host that is also forwarded by IP and port (portForward: auto), for a client that cannot use the hostname. Fails when the host is not forwarded.
forward:web+url:webSeveral sources in one value, joined with +: each is resolved, a duplicate is dropped (the first stays), and the order is the one written. They are joined with the separator named after the last one, forward:web+url:web:space (also origins+forward:web:newline), comma by default. A list source (origins, hosts) contributes all of its items. A forwarded address whose port is not chosen yet is left out of a combination rather than failing it; a host that does not exist is an error.

An unknown source fails the start and names the valid ones, rather than leaving a variable quietly empty to surface much later as a confusing runtime error.

It beats env_file

These land in the generated fragment, merged last, so they override the service's own environment: and any env_file:. A static list of origins in a committed .env therefore stops being what the universe runs with — the usual reason CORS is wrong in a second copy of a stack.

A service that reads a file and not its environment cannot use a label. The app's render entries write that file from the same sources, as template functions of the same names: Write a config file from the universe's addresses.

Prefer origins and hosts to naming addresses one at a time: they follow the manifest, so adding a host key or an app leaves no settings list behind.

Where multiversectl reads them

From the merged configuration of the app's files, at two moments: when a universe is created, so urls and ls can answer without a running container, and again on every start, because the files may have changed. Nothing is cached beyond the universe's state file, so a label added to a repository takes effect on the next up — no manifest change, no re-creation.

Compared with other tools

Compose stacks per worktree, agent sandboxes, Tilt, Skaffold, Garden, preview environments: what each is for, and when to pick it instead.

The short version

multiversectl is for one thing: a whole, working copy of a system that spans several repositories, as many times as you need, on one machine, from the compose files you already have. A copy has every repository checked out on its branch, every app running, its own data, and addresses that behave like a real environment's: hostnames another device can open, and the origins and URLs a framework checks, handed to the services that need them.

Plenty of good tools sit next to it. Most of them solve a neighbouring problem better, and the honest way to choose is by what you are optimising for. This page says when to pick each one instead. It describes them as their own documentation does in October 2026; they move quickly, so check theirs before deciding.

A compose stack per worktree

The closest neighbours. Docktree, BranchBox, treehouse and treerig each take a git worktree of one repository and give it its own compose project, so several branches run at once without colliding. They are simple to adopt when your system is a single repository, and they start from a worktree, so one that an agent manager made is a natural fit. Some, Docktree among them, also share heavy services: one database server with a database per worktree, which multiversectl does not do yet.

Where multiversectl differs:

  • The copy is the whole system. A universe is a worktree of every repository, on a branch that is the same everywhere unless you say otherwise, created, started, listed and removed as one. An API in one repository and the front end that calls it in another are one universe, not two stacks you keep in step.
  • Hostnames, not ports. Each address is a name such as api-u3.192-168-1-20.traefik.me that any device on the network resolves, a phone included, behind one proxy. A port per copy avoids collisions, but cookies, OAuth callbacks and CORS rules are written for names.
  • The universe tells the services where they are. <NAME>_URL, MULTIVERSE_ORIGINS and labels such as dev.multiversectl.env.CSRF_TRUSTED_ORIGINS: origins hand each copy its own addresses, so a framework that checks the origin works in every copy without editing anything.
  • A life, not only a start. Hooks seed data and register addresses and take them back on removal, rendered files give a config file the universe's values, and doctor asks every address whether it answers.

Agent sandboxes and worktree managers

container-use gives each agent a container on a branch of its own; claude-squad, Conductor and similar tools run several agents, each in a worktree. They isolate the agent and its files. What they do not do is run the system the agent changes: two agents in two worktrees still fight over the same ports, containers and database.

That is the part multiversectl does, so the two combine: give each agent a universe and point it at that universe's checkouts. --json on every command and the skill from multiversectl agents skill install tell an agent how. To run code you do not trust, use a sandbox or a VM: a universe is not a security boundary.

Tilt, Skaffold, Garden and Signadot

Tilt and Skaffold make the edit, rebuild and look loop fast for one environment, usually on Kubernetes. Running several copies with them is possible, a namespace or a set of ports each, but it is yours to arrange. Garden makes a namespace per branch or developer with a copy of every service; Signadot keeps one shared baseline and forks only the services a branch changes, which scales to systems far larger than a laptop.

If you deploy to Kubernetes and the cluster is where development already happens, those are the better fit. multiversectl is for the many systems whose development stack is docker compose, where nobody wants a cluster to get a second copy. It does not rebuild on save itself: what reloads is whatever your compose files already do, a bind mount and a dev server.

Preview environments and remote workspaces

Preevy, PullPreview and Uffizzi make a copy per pull request on a cloud machine or a cluster, reachable from anywhere, made by CI. Dev Containers, DevPod, Coder and Gitpod give each person or branch a development machine with the toolchain installed.

multiversectl makes its copies on your machine, in seconds, on the image cache and daemon you already have, and they cost nothing to keep. A universe can be opened from another device on your network, not from the internet. When a reviewer outside it needs the branch, or the copy should exist before anyone checks it out, a preview environment is the tool.

Doing it by hand

git worktree add and docker compose -p get you most of one copy of one repository. What multiversectl adds is everything after that, for every repository at once:

  • a branch and a worktree in each repository, created and removed together, and a branch deleted only once its work is elsewhere;
  • published ports dropped and routing labels generated, so your compose files stay the ones you run without it;
  • hostnames, origins and URLs worked out and handed to services, secrets copied in, config files rendered;
  • one view of every copy, in the terminal and in a browser, with what each branch adds and its pull request.

Where multiversectl is weaker

  • Every universe runs everything. Each copy has its own database, broker and caches. That is what keeps one branch's schema out of another's, and it is also what limits you to as many copies as the machine's memory holds. Sharing one server among universes is not there yet.
  • docker compose only, one machine. No cluster, no remote host.
  • One proxy per machine. Two multiverses that disagree about its entrypoints take it from each other, and say so when they do.
  • Not isolation. Universes share the kernel, the daemon and your user; see It is not a virtual machine.
  • Before 1.0. The manifest's fields can still change between releases.

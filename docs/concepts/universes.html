Universes

What a universe is made of, how it is named, and what it does and does not share with the others.

What a universe is made of

Creating one is four things on disk and nothing else:

  • A worktree of every repository, under <root>/universes/<id>/<repo>, checked out on the universe's branch. They are real directories you edit with your own editor and your own git.
  • A compose project per app, named <project>-<slug>-<app>, which is what namespaces containers, networks and volumes.
  • A set of hostnames, one per host key, resolved when the universe is created and refreshed on every start.
  • A state file, universe.yaml, holding all of the above plus when it was created, when it last started and why it exists.

Nothing is copied that git already has: every worktree shares the clone's object store, so ten universes of a large repository cost ten checkouts, not ten histories.

Numbered or named

$ multiversectl universe new 3           # branch u3, hostnames api-u3.<domain>
$ multiversectl universe new fix/login   # branch fix/login, api-fix-login.<domain>

A universe is identified by the name you typed. Everything else about its identity is derived from it, so there is one place to look:

Derived3fix/login
Directoryuniverses/3universes/fix-login
Slug, in hostnames and projectsu3fix-login
Default branchspec.branch, u3 by defaultthe name itself

The slug is the name reduced to what DNS labels and compose project names both accept, so feat/ARCA-123 is reachable at api-feat-arca-123.<domain> while the branch keeps its real name. A name whose slug would not fit in a DNS label is refused, with the limit named, rather than truncated into a collision with another universe.

Every command takes whichever of the three you happen to be looking at — the name, the directory or the slug — because all three are in front of you at different moments. up fix/login, up fix-login, up 3 and up u3 all find their universe, and an unknown name lists the ones that exist.

Branches, and never clashing

A universe checks out one branch per repository, and it gets there in one of two ways that never mix.

A new universe starts branches of its own. In every repository it makes a branch that exists nowhere yet, from the base branch, so it can never land on anyone's work. Unless you say otherwise a numbered universe's branch renders spec.branch and a named one's is its name:

spec:
  branch: dev/u{{universe}}   # default: u{{universe}}

Before anything is created every repository is looked at, after fetching it, so a branch someone pushed an hour ago counts. If a branch exists in the clone or on origin in any repository, nothing is created: every clash is listed with the three ways out (leave the name out, check the branch out instead, or delete a leftover branch you do not need). If a later repository fails, what was added is taken back, and the number is free again. New branches start from origin/<base> as fetched, not from the clone's own copy of the base, which is routinely behind; --base starts them somewhere else, and --branch names them, repeatably: a bare name is every repository, repo=name is one.

$ multiversectl universe new                       # the next free number
$ multiversectl universe new 3 --base release/1.2
$ multiversectl universe new 3 --branch feat/invoicing --base api=release/1.2

The next free number is not just the next number no universe has. It also steps over a number whose branch still exists in any repository, and says which it skipped and why. That is what a removed universe can leave behind when its branch held work that was nowhere else.

A checkout universe works on a branch that already exists. It is named after the branch (--name for another), checks it out in every repository that has it, tracking origin when it is only there, and refuses what would be a mistake: a branch checked out in another universe or in the shared clone (git allows a branch in one worktree only, and the place is shown), or one that exists in no repository, so a typo never becomes a branch. A repository that lacks the branch gets a new one of that name from its base, or with --only-existing is left on its base, detached.

$ multiversectl universe checkout fix/login
$ multiversectl universe checkout fix/login --repo web=feat/ui --only-existing

Removing a universe deletes only the branches it started, and only when nothing is lost. A branch goes when every commit on it is already on the base branch or on the branch's own remote copy. One that holds commits that are on no remote is kept, and rm says so and how to delete it yourself. A branch a universe only checked out is never touched. Universes made before this was recorded keep their branches, since nothing says they were theirs.

What a universe remembers

A universe that has been sitting there for a week should still be identifiable, so its state file keeps more than the routing:

# ~/acme/universes/fix-login/universe.yaml
name: fix/login
id: fix-login
slug: fix-login
created: 2026-10-25T10:44:09Z
lastStarted: 2026-10-25T10:46:11Z
note: PR 412 review
manifest: /home/me/work/acme/multiverse.yaml
version: 0.0.1

Set the note when you create it, and ls shows it beside the name:

$ multiversectl universe new fix/login --note "PR 412 review"

ls -o wide adds the ages — created 3d ago · last started 2h ago — which is usually how you decide which universe to reclaim.

Lifecycle

CommandWhat changes
newWorktrees, secrets, state. Nothing starts. Safe to run again: existing checkouts are kept, and a repository added to the manifest since is added to the universe.
upBrings up the shared proxy, regenerates the routing, starts each app. Idempotent.
downStops containers. Volumes and checkouts stay, so starting again is where you left off.
rmDestroys containers, volumes, worktrees and state. Asks first, and requires the universe's name typed back.

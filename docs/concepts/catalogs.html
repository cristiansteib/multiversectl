Catalogs

An index of projects and of other indexes, kept in git, that says what exists and leaves what is installed to each machine.

What a catalog is for

A project manifest describes one project. A catalog answers a different question: which projects exist, and which belong on this machine. It holds pointers, so manifests stay with the repositories they describe.

Catalogs nest. A personal catalog can link one a team keeps in its own repository, which can link another; each layer is edited by whoever owns that repository, and a machine installs only the branches it wants.

You do not need one: multiversectl project install acme/multiverse works with no catalog at all. The catalog is for keeping your own index of what you work on.

Catalog, CatalogRef and ProjectRef

apiVersion: multiverse/v1alpha1
kind: Catalog
metadata:
  name: me
spec:
  catalogs:                         # CatalogRef: descend into another Catalog
    - name: acme
      source: {repo: git@example.test:acme/multiverse-index.git, ref: main}
    - name: personal                # no repo: a file in this same repository
      source: {path: catalogs/personal.yaml}
  projects:                       # ProjectRef: a leaf
    - name: notes
      source: {repo: git@example.test:me/notes-project.git}
FieldMeaning
source.repoA git URL. Leave it out to mean the repository the reference is written in.
source.refBranch, tag or commit. Needs repo. A tag or commit makes that layer read-only.
source.pathRelative to the repository root, and cannot leave it. Defaults to catalog.yaml or multiverse.yaml.

A node is addressed by the names leading to it, such as acme/backend/billing; names are unique among siblings. The schema is schema/catalog.v1alpha1.yaml.

Where a node lives

A repository is written as a URL, which says how it was typed rather than where it is, so everywhere one is shown the platform comes first:

You seeIt is
github:acme/apia repository on GitHub, however its URL was written
gitlab:acme/team/apia project on GitLab, subgroups included
git:git.example.test/acme/apia repository on any other host, with the host named
file:~/code/index/catalog.yamla file or directory on this machine

A branch, tag or commit follows as @ref, and self-hosted servers keep their host: gitlab:gitlab.example.test/acme/api. The tree says what each node is, whether each project is installed, how many are installed under each catalog, and the file inside a repository when two catalogs share one:

$ multiversectl catalog
index     root       github:me/index                              1/2 installed
├─ personal  catalog    github:me/index catalogs/personal.yaml  0/1 installed
│  └─ notes     project  file:~/notes/multiverse.yaml           ○ not installed
└─ acme      catalog    gitlab:acme/index                            1/1 installed
   └─ billing  project  gitlab:acme/billing                        ✓ installed as billing

The web page draws the same, with each platform's mark and a badge for root, catalog or project.

The root, and how a new machine finds it

Every machine starts from one catalog, its root, which has its own kind so it can be told from the catalogs hanging under it:

apiVersion: multiverse/v1alpha1
kind: CatalogRoot
metadata:
  name: me

A CatalogRoot is a Catalog in every other respect, and one listed under another catalog is just a catalog there. The kind only tells init where to start.

On a hosting service the root's repository also carries the topic multiversectl-root. init sets it, and on a machine with nothing it searches your repositories and organizations for that topic without cloning. A root made before the kind existed is a plain Catalog, and init offers to mark it.

Three separate things

  • The catalog is shared and versioned: what exists. Pointers, never definitions.
  • The project list is per machine, in ~/.config/multiversectl/config.yaml: what is installed here, which is current, and where each came from.
  • Universes act on one project and never read a catalog.

Only install connects the first two, and it only reads. catalog add, create and rm are what edit a catalog.

Names

A project is installed under its own name, billing, in ~/multiverse/billing. If that is taken, the name above goes in front (payments-billing), and --name overrides. The name does not change afterwards, so -w billing in a script survives a reorganised catalog. Anywhere a project name is accepted, so is the catalog path it was installed from: use acme/backend/billing.

Each installed project records where it came from, which is how status and update know it has drifted.

When a layer cannot be read

A layer you have no access to, or with a bad file, shows as unavailable with the reason, and the rest of the tree still resolves. Cycles and chains deeper than eight levels are cut off the same way.

Several projects, one proxy

A machine has one proxy, and starting any project rewrites it from that project's manifest. Sharing its network and the default web port is normal; wanting a different entrypoint, network or bind address is not, because starting the second project takes the proxy from the first. install and doctor name those differences, by project.

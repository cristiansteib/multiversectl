Catalogs

An index of multiverses and of other indexes, kept in git, that says what exists and leaves what is installed to each machine.

What a catalog is for

A multiverse describes one set of repositories. A catalog answers a different question: which multiverses exist, and which belong on this machine. It is only an index, and holds pointers, so each definition stays with the repositories it describes.

Catalogs nest. A personal catalog can link one a team keeps in its own repository, which can link another; each layer is edited by whoever owns that repository, and a machine starts only the multiverses it wants.

You do not need one: multiversectl start acme/multiverse works with no catalog at all, and a repository can hold several multiverses without any catalog listing them. The catalog is for keeping your own index of what you work on.

What a catalog lists

An entry is a multiverse or another catalog. They are two lists because the file has to say which is which: drawing the tree would otherwise mean cloning every entry to find out. Everything else treats them alike, so catalog add and catalog rm take either.

apiVersion: multiverse/v1alpha1
kind: Catalog
metadata:
  name: me
spec:
  catalogs:                         # descend into another Catalog
    - name: acme
      source: {repo: git@example.test:acme/multiverse-index.git, ref: main}
    - name: personal                # no repo: a file in this same repository
      source: {path: catalogs/personal.yaml}
  multiverses:                     # a Multiverse, a leaf
    - name: notes
      source: {repo: git@example.test:me/notes-multiverse.git}
FieldMeaning
source.repoA git URL. Leave it out to mean the repository the entry is written in.
source.refBranch, tag or commit. Needs repo. A tag or commit makes that layer read-only.
source.pathRelative to the repository root, and cannot leave it. Defaults to catalog.yaml or multiverse.yaml; a second multiverse in the same repository is multiverse/<name>.yaml.

An entry is addressed by the names leading to it, such as acme/backend/billing; names are unique among siblings. The schema is schema/catalog.v1alpha1.yaml.

Where a node lives

A repository is written as a URL, which says how it was typed rather than where it is, so everywhere one is shown the platform comes first:

You seeIt is
github:acme/apia repository on GitHub, however its URL was written
gitlab:acme/team/apia repository on GitLab, subgroups included
git:git.example.test/acme/apia repository on any other host, with the host named
file:~/code/index/catalog.yamla file or directory on this machine

A branch, tag or commit follows as @ref, and self-hosted servers keep their host: gitlab:gitlab.example.test/acme/api. The tree says what each node is, whether each multiverse is installed, how many are installed under each catalog, and the file inside a repository when two catalogs share one:

$ multiversectl catalog
index     root       github:me/index                              1/2 installed
├─ personal  catalog    github:me/index catalogs/personal.yaml  0/1 installed
│  └─ notes     multiverse file:~/notes/multiverse.yaml           ○ not installed
└─ acme      catalog    gitlab:acme/index                            1/1 installed
   └─ billing  multiverse gitlab:acme/billing                        ✓ installed as billing

The web page draws the same, with each platform's mark and a badge for root, catalog or multiverse.

The root, and how a new machine finds it

Every machine starts from one catalog, its root. It is an ordinary Catalog; what makes it the root is that this machine points at it, and that init tags its repository with the topic multiversectl-catalog.

On a hosting service init sets that topic, and on a machine with nothing it searches your repositories and organizations for it without cloning, so a new machine finds its index by itself.

Three separate things

  • The catalog is shared and versioned: what exists. Pointers, never definitions.
  • The multiverse list is per machine, in ~/.config/multiversectl/config.yaml: what is started here, and where each came from.
  • Universes act on one multiverse and never read a catalog.

Only start connects the first two, and it only reads. catalog add, new and rm are what edit a catalog.

Names

A multiverse is installed under its own metadata.name, billing, in ~/multiverse/billing. Names are unique on a machine: a second multiverse with the same name is refused, naming the file that defines it, so rename one of them there. Commands that act on one take -m billing; without it, the one whose folder you are in, else the only one installed. Anywhere a name is accepted, so is the catalog path it was installed from: acme/backend/billing.

Each installed multiverse records where it came from, which is how status and catalog update know it has drifted.

When a layer cannot be read

A layer you have no access to, or with a bad file, shows as unavailable with the reason, and the rest of the tree still resolves. Cycles and chains deeper than eight levels are cut off the same way.

Several multiverses, one proxy

A machine has one proxy, and starting any multiverse rewrites it from that multiverse's manifest. Sharing its network and the default web port is normal; wanting a different entrypoint, network or bind address is not, because starting the second multiverse takes the proxy from the first. start and doctor name those differences, by multiverse.

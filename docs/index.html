What it is

multiversectl gives a system that spans several repositories as many complete, working copies as you need, on one machine. Each copy is a universe, numbered or named after the branch it checks out, and it has all of it: a git worktree of every repository, every app running as its own compose project, its own data, and hostnames that open from any device on your network. So a branch to review, a migration to try or an agent to let loose each gets a whole environment, while yours keeps running.

It namespaces instead of virtualizing. A new universe is a worktree and a compose up: seconds, on the daemon and image cache you already have, from the compose files you already run. The addresses are the part most tools leave to you: one shared proxy routes by hostname, and each universe hands its own URLs and origins to the services that check them, so logins, callbacks and CORS work in every copy.

What it does

The features that matter most, and where each is explained.

FeatureWhat you getRead more
The whole system per copyA worktree of every repository on one branch, every app running, created, started, listed and removed as one. Numbered (3) or named after its branch (fix/login); one repository can follow another branch, or an existing one.Work across branches
Shared in one commandSomeone points you at a multiverse and multiversectl start acme/platform (owner/repo, any git URL, or a path) clones every repository it names, makes a universe and runs it, with nothing set up first. A repository can hold several multiverses: start billing acme/platform picks one. A repository with only a compose file runs as itself.Quick start, Catalogs
Hostnames, not portsOne shared proxy routes api-u3.<domain> to the right copy. No universe publishes a port, so nothing collides and nothing needs port arithmetic.Networking
Open it from any deviceWith expose: lan every address resolves on your network, a phone included, with nothing installed; local keeps it to this machine; a domain of your own, or none at all and an IP and port per host.Reach a universe
Addresses handed to the servicesAPI_URL, MULTIVERSE_ORIGINS and labels such as dev.multiversectl.env.CSRF_TRUSTED_ORIGINS: origins give each copy its own URLs and origins, so logins, callbacks and CORS work everywhere.Labels, Variables
HTTPSAn entrypoint marked tls, with your own wildcard certificate or the proxy's, and every address then says https://. Backends that speak TLS or gRPC are reached with scheme.Serving https
Your compose files, unchangedA repository with one exposed port needs no configuration; labels say the rest and do nothing when you run compose by hand. What only this environment needs goes in an overlay.Labels, Overlays
A database per copyVolumes are namespaced per universe, so a migration on one branch never touches another's data, and removing a universe removes exactly what was its own.Storage and data
HooksCommands tied to a universe's life, in a container or on the machine: seed a user once, register the address with an identity provider, take it back on removal. Retries and failure policies included.Hooks
Rendered config filesA config file the app reads at startup, written from a template and the universe's values, kept out of git's sight.Render
SecretsFiles git does not hold, such as .env, copied into each universe from the clone, made from a template when missing; doctor fails before a universe half-starts without one.Secrets
Optional and on-demand appsGroups of services started with --with, and apps that run only when named, so a copy starts what you need.Optional, Autostart
Keep branches currentuniverse sync fetches and moves each checkout forward to what it follows, with --merge for one that has commits of its own; a branch is deleted with its universe only once its work is elsewhere.Commands
doctorChecks the machine, the proxy, the secrets and every address, and tells a running app from the proxy's own error pages.Troubleshooting
A web viewEvery universe, its containers, logs and use of the machine; what each branch adds and its pull request; buttons to start, stop, create and remove; pair a phone to it.In a browser
CatalogsAn index of multiverses kept in git, which can nest other people's: a team says what exists, each machine installs what it needs.Catalogs
Made for agents too--json on every command, --help --json to describe one, and a skill that tells an agent to work in a universe of its own.Agents

What it is not

Knowing where it stops saves trying it for the wrong job.

It is notBecauseFor that, use
A sandbox or a VMUniverses share your kernel, daemon and user: one can fill the disk or reach another's containers. They are copies you trust, not a boundary.A VM, or a container sandbox for untrusted code
A replacement for docker composeIt describes no containers. It reads your compose files and adds only routing and names, so they keep working without it.The compose files you have
A rebuild-on-save loopWhat reloads in a universe is what your compose files already do: a bind mount and a dev server.Your dev server; Tilt or Skaffold on Kubernetes
A deployment or production toolIt runs on one machine, for development. Nothing it does belongs on a server others depend on.Your deployment pipeline
A preview service on the internetA universe answers on this machine or its network, not to the outside world, and is made by you, not by CI.A preview-environment service
An agent runnerIt gives an agent a whole environment to work in; it does not start, prompt or supervise the agent.Your agent, or a worktree manager, pointed at a universe
A way to share one database among copiesEach universe runs its own services, data included. That keeps branches apart, and it is what the machine's memory has to hold.Fewer universes, or lighter services in an overlay

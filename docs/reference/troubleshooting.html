Troubleshooting

Hostnames that do not resolve, ports in use, missing secrets and dev servers that answer 403.

A universe runs old code, or a label that exists is not found

up says service "mailpit" exposes 2 ports, so which one serves api is a guess — add a label, yet the compose file on main has that label. A universe's checkouts keep the commit they were made from and do not follow main. When that may be the cause, the error ends with this universe's code is out of date and names the repositories and how far behind they are.

$ multiversectl universe sync 1
$ multiversectl universe up 1

sync never touches uncommitted changes, and leaves the universe's own commits alone unless --merge. universe status and the web page warn when a universe is behind; catalog update keeps the clones current.

Hostnames do not resolve

doctor warns: does not resolve; a router or local DNS server may be stripping private-IP answers. Some routers and resolvers drop DNS answers that point to private addresses. Compare your resolver with a public one:

$ dig +short app-u3.192-168-1-20.traefik.me
$ dig +short app-u3.192-168-1-20.traefik.me @1.1.1.1

Empty from the first and an address from the second means your resolver strips it. Allow private answers for that domain (often called DNS rebinding protection), point the device at another resolver, or use a domain you own.

Port 80 or 8001 is already in use

doctor fails with entrypoint web needs port 80, which is taken by another process when the proxy is not running yet. Find the owner and stop it:

$ ss -ltnp 'sport = :80'
$ multiversectl universe doctor

Or move the entrypoint in the manifest (spec.proxy.entrypoints); urls then prints the port.

A secret file is missing

up stops and names each missing file and where it belongs; doctor 3 fails with secret <app>: missing <path>. Files under an app's secrets: are copied from the clone into each universe, and a tracked .env.example (or the file the app's secretTemplates names; "" turns this off) is used when the clone has none. Otherwise put the file in the clone and start again:

$ cp .env ~/acme/api/.env
$ multiversectl universe up 3
$ multiversectl universe doctor 3

Removing a universe leaves files only root can delete

A container that runs as root writes into the worktree it mounts — a node_modules, a build cache, sometimes a file in the source tree — and those files belong to root. Nothing you run as yourself can delete them, so universe rm asks a throwaway container, which is root, to remove them (alpine, pulled the first time, no network, nothing mounted but the universe's folder). You need nothing to do.

Only when that cannot run either, Docker being unreachable or the image not pullable, does it fall back to leaving the universe listed, and saying what is left:

error: universe 2: its containers and volumes are gone, but this is still on disk:
    ~/acme/universes/2/admin: unlinkat …/.angular/cache/…/.tsbuildinfo: permission denied
  Files owned by another user, which a container that runs as root leaves behind. Remove them with:
    sudo rm -rf ~/acme/universes/2/admin
  Then run `multiversectl universe rm 2` again to finish.

Do that and the second rm finishes the job. To stop the files being made at all, have the service run as you — most images take a user:, and ${HOST_UID}:${HOST_GID} are passed to every compose file for exactly this.

A dev server answers 403

Many dev servers reject Host headers they do not know, and a universe answers on app-u3.<domain>. Allow it with the variable the manifest passes in, through an inline overlay — the variable name is whatever your server reads:

apps:
  - name: web
    repo: web
    overlay:
      services:
        app-dev:
          environment:
            ALLOWED_HOSTS: "${APP_HOST}"

Also check that the hostname is the one multiversectl universe urls 3 prints, and that the service has the label or the single port that routes it.

A compose project belongs to another multiverse root

up, down or rm stops with compose project acme-u1-api already has containers started from …, which is not universe 1. A universe's compose project is named after its multiverse and the universe, so two roots that would give the same universe the same name share containers and volumes: starting one recreates the other's, and removing one deletes the other's data. Before it acts on a project, multiversectl checks the working directory and compose file the existing containers were started from and refuses when they are not under this universe. universe rm skips such a project with a warning and still removes the rest.

A multiverse installed under a name other than its manifest's (start owner/repo --as copy) puts that name in its compose projects (acme-copy-u1-api), so the clash does not arise for new installs; an install that predates this keeps the project it was created with until it is brought down and started again. An install named like its manifest keeps its project names unchanged.

$ multiversectl start owner/repo --as copy

A service with network_mode is not reachable through the proxy

The proxy reaches a service by joining one of its app's networks, and a service in another network mode (host, or service:other) is on none of them. So such a service is left out of the fragment: up warns service "web" sets network_mode "host", so it is on none of its app's networks and host web-u1.example.test cannot be reached through the proxy, and the rest of the app starts. A portForward on that host is dropped with it, because the fragment cannot publish a port for such a service either; reach it on the host's own network, or route to a service on one of the app's networks instead.

Starting a universe would reconfigure the shared proxy for other multiverses

One machine has one shared proxy. A multiverse whose expose, proxy entrypoints or TLS differ from the running proxy's would rebind it, and every universe of any other multiverse served through it would stop answering. When another multiverse has containers running, up refuses, says what would change and who would be affected, and changes nothing:

error: this multiverse needs the shared proxy published on 127.0.0.1 instead of 0.0.0.0, which would stop
universes of beta from answering: nothing was changed. …

Match the settings (the multiverse's expose, entrypoints and certificates), stop the other universes first, or pass --rebind-proxy (on universe up, start and system proxy up) to reconfigure it anyway; the others answer again when started from their own multiverse. With nothing else running the proxy is rebound with a warning, as before.

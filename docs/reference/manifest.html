Manifest

Every field of a multiverse manifest, with its default.

Two kinds of file

There are two kinds, and only two. A Multiverse says which repositories are needed and how a universe of them is addressed. A Catalog is an index: it lists multiverses and other catalogs, and holds no definition itself. A universe, the running copy, has no file of its own to write.

A repository can hold several multiverses, one file each, in files of any name and anywhere in the repository: a .yaml or .yml file that says kind: Multiverse is one, so nothing has to list them (dependency, build and dot folders are not searched; multiverse.yaml at the root and the files of multiverse/ are always taken). multiversectl start name owner/repo, or start owner/repo:name, picks one by its metadata.name; with no name and several to choose from it asks at a terminal, and lists the names in a script. Two files with the same name are refused. Names are unique on a machine: a second multiverse with a name already installed is refused, naming the file.

A repository with compose files and no multiverse needs no definition at all: multiversectl start owner/repo, or start . in a checkout, runs it as a multiverse of one — itself, named after the repository. The manifest it runs from is made for you and kept in the multiverse's own folder (.multiverse/multiverse.yaml), never written into the repository; say more with a .multiverse.yaml in the repository (services, secrets, optional groups), or add a multiverse.yaml and that is what gets installed instead. When the repository's name is already taken by another multiverse, the newcomer takes the next level of its address (owner-repo, then host-owner-repo) and says so; the one already installed is never renamed, and --as <name> picks the name outright. A name written in a manifest is not stretched this way: a clash on it is refused.

What a repository says about itself

A multiverse can be nothing but the list of its repositories. Each repository then says how it runs in a .multiverse.yaml at its root: the same apiVersion and kind: Multiverse, but about that one repository, so it lists no repos and sets nothing that belongs to the whole multiverse. Only spec.apps and spec.proxy.entrypoints are read from it. When the multiverse declares an app of the same name for that repository, the repository's app is the starting point and what the multiverse sets goes on top: a list it gives (services, hosts, hooks…) replaces the repository's, and env and secretTemplates are merged key by key. What only the replaced lists needed goes with them: a template for a secret the multiverse no longer lists, a defaultService it no longer runs. The multiverse's app is still checked on its own first, so what it names must be among what it says.

apiVersion: multiverse/v1alpha1
kind: Multiverse
metadata:
  name: api
spec:
  proxy:
    entrypoints:
      - {name: devapi, port: 8001}   # the port its front-ends call
  apps:
    - services: [web, mailpit]            # name and repo are the repository's: leave them out
      secrets: [.env]

An app in it belongs to that repository, and takes the repository's name when it is the only one. It replaces the app the multiverse would have derived for the repository; it cannot take another app's name, and an entrypoint must be on the same port everywhere it appears. The file is read from the repository's clone in the multiverse root, so it changes when the clone is updated. It is a dotfile so it is never mistaken for a multiverse of its own (multiverse.yaml, multiverse/*.yaml). Compose labels stay the layer for each service.

One multiverse.yaml lists the repositories and how a universe is addressed. It never describes containers; those stay in each repository's own compose files. The format is versioned, Kubernetes-style: apiVersion: multiverse/v1alpha1, kind: Multiverse.

apiVersion: multiverse/v1alpha1
kind: Multiverse
metadata:
  name: acme
spec:
  expose: lan
  domain: auto
  repos:
    - name: api
      url: git@github.com:acme/api.git
    - name: web
      url: git@github.com:acme/web.git

That is a complete multiverse. A repository no apps entry names gets an app of its own name, so apps: is only for changing a default or splitting one repository into several apps.

Every field, with its meaning and default, is in schema/multiverse.v1alpha1.yaml. That file is generated from the Go types by make schema; see also the commented examples/multiverse.yaml. The main keys:

KeyMeaning
metadata.nameNames the multiverse; prefixes every compose project (acme-u3-api).
spec.rootWhere clones and universes live. --root and $MULTIVERSECTL_ROOT override it.
spec.exposeWho can reach a universe: lan (default) or local. Decides both the interface the proxy publishes on and what auto derives — see Networking.
spec.domainWildcard domain for hostnames. Default auto, which follows expose.
spec.branchBranch template for a numbered universe; {{universe}} expands to the number. Default u{{universe}}. A named universe uses its own name.
spec.proxyProxy network and named entrypoints (web on 80 by default).
spec.repos[]name, url, base (the branch a universe's branch starts from and is measured against; default the remote's default branch, --base overrides it), and dir only when the folder is not the repository's own name (acme-api for .../acme-api.git). A repository with no compose file is checked out and nothing starts for it.
spec.apps[]name, repo, compose, profiles, services, optional (a name, which is also a compose profile, and the services it adds; leave those out when the profile says, unless the app names its services), env (variables for this app only, over spec.env), autostart (default true; false leaves the app out of a start that names no app — see Services), secrets, secretTemplates (the file a missing secret is made from; default <name>.example, "" for none), hooks (postCreate, preUp, postUp, preDown, postDown, preRemove; each in a container or on the host — see Services), render (files made from a template and the universe's addresses, before the app starts; to, template or from, mode, overwrite — see Services), publish, defaultService (where exec and run go when the app has several services), overlay, hosts (each may set portForward, alsoMatch, and scheme: http, https or h2c for a gRPC service), build.
spec.hooksThe same events for the whole multiverse, on the machine only: postUp runs once every app is up.
spec.env[]Variables exported into every runtime call; {{uid}}, {{gid}} and ${VAR} expand.

hosts: for repositories you cannot change

Labels are the better place to say how a service is reached. hosts: on an app wins over them and exists for repositories you cannot edit:

hosts:
  - name: api            # api-u3.<domain>
    service: web
    port: 8001
    entrypoint: devapi    # default: web
    alsoMatch: [app, adm]  # other host keys, same service

portForward: reachable by IP and port

A client that refuses plain http to a hostname (an iPhone app) needs an address it may call. portForward: auto on a host publishes it on a free host port too:

hosts:
  - name: api
    service: web
    port: 8000
    portForward: auto    # http://<this machine's address>:<free port>

The kernel picks the port once; it is kept in the universe's state, so the address survives restarts, and no other universe gets it. It binds like the proxy: every interface with expose: lan, loopback only with expose: local. universe ls shows it as <host>:forward. A host from a compose label asks for the same with dev.multiversectl.host.api.portForward: auto.

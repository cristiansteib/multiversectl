Networking

One shared proxy, one hostname per address per universe, and why no universe publishes a port of its own.

The problem it solves

Two copies of the same stack cannot both publish port 8000. The usual answer is to give the second copy other ports, then teach every front-end, callback URL and developer about them. multiversectl allocates no ports: every universe is reached through one shared proxy on one set of ports, and requests are told apart by the Host header. The tenth universe costs no ports and changes no configuration anywhere.

The shared proxy

One Traefik container for the machine, in its own compose project multiverse-proxy. The first up starts it. It discovers routes from the container runtime, so starting a universe is all the configuration it needs; multiversectl writes the labels into a generated fragment, one per app, which is why your own compose files say nothing about Traefik:

# universes/3/.multiverse-routes-api.yml, rewritten on every up
services:
  web:
    ports: !reset []
    labels:
      traefik.enable: "true"
      traefik.docker.network: "acme-u3-api_default"
      traefik.http.services.api-u3.loadbalancer.server.port: "8001"
      traefik.http.routers.api-u3.rule: "Host(`api-u3.example.test`)"
      traefik.http.routers.api-u3.entrypoints: "web"

The proxy reaches a service on the app's own network — the network compose puts it on, read from the resolved configuration, which is the project's default network (acme-u3-api_default) unless your compose files name one themselves — and joins it once the app is up: a connection made to the running proxy, which is neither restarted nor recreated when a universe comes or goes. It leaves the network before the app is taken down. Services are not attached to any network shared with other universes, on purpose: on a network every service answers to its plain name, so auth there would be the auth of every universe at once, and a service calling http://auth:8080 would reach a random universe's. A host reached by IP alone (portForward: only, domain: none) has no route in the proxy and is on no proxy network at all.

The proxy's own compose file still names one network, multiversenet by default, so older universes keep answering until they are brought up again; universe doctor lists the containers still on it. A proxy that is created again joins the networks of the containers that name it in their io.multiversectl.served-by label, and it leaves every network of an app's compose project before that app is taken down.

Each network takes a subnet from Docker's address pools, which bound how many networks the machine can have. doctor reports how many are left, because the failure — all predefined address pools have been fully subnetted — says nothing about what to change.

Edit the manifest or your compose files, never the generated one: it is replaced on every start.

Entrypoints

An entrypoint is a named port the proxy listens on, shared by every universe.

spec:
  proxy:
    entrypoints:
      - name: web
        port: 80
      - name: devapi
        port: 8001

One is usually enough. The second is for a browser application built to call its API on a fixed port: point the proxy at that port too and the API answers there under every universe's own hostname, so the hard-coded :8001 keeps working everywhere, unchanged. A host rule picks its entrypoint by name, defaulting to web.

Hostnames

Every address is <host-key>-<slug>.<domain> — the host key names the address, the slug names the universe:

api-u3.example.test         # host api, universe 3
adm-u3.example.test         # host adm, universe 3
api-fix-login.example.test  # host api, universe fix/login

Flat rather than nested, on purpose: api-u3.example.test is one label under the domain, so a single wildcard certificate for *.example.test covers every address of every universe. api.u3.example.test would need one per universe, because a wildcard matches one label.

A service can claim several hostnames, which is how one API answers under each front-end's own name — see Labels.

Domains

spec.domain is the wildcard domain hostnames are built under. The default, auto, derives one from how the multiverse is exposed.

Serving https

Give an entrypoint tls: true and the proxy serves every host on it over https. Every address handed to a service or shown (<NAME>_URL, MULTIVERSE_ORIGINS, universe ls) then says https://, so a framework that checks the Origin header sees the one the browser sends. With no certificate the proxy presents its own self-signed one; for a domain you own, name a wildcard certificate for *.<domain> and it covers every universe:

spec:
  domain: dev.example.com
  proxy:
    entrypoints:
      - {name: web, port: 443, tls: true}
    certificates:
      - {certFile: ~/certs/wildcard.pem, keyFile: ~/certs/wildcard-key.pem}

The certificates are files on the machine, mounted into the proxy read-only; a relative path is relative to the manifest. A renewed certificate is read when the proxy next starts. A forwarded address (portForward) reaches the service without the proxy and stays http://.

Without any DNS name

The default lan setting builds names under a public wildcard service, which puts your machine's address in a stranger's DNS logs and needs a resolver that answers it. domain: none opts out entirely:

spec:
  expose: lan       # 0.0.0.0, so another device can reach it
  domain: none      # and no name anywhere

Each host is published on a free port of its own on the machine's address (the portForward mechanism, applied to every host), and that http://<ip>:<port> is what ls, the web view, <HOST>_URL and origins show. The port is chosen once and kept for the life of the universe. With expose: local it is 127.0.0.1. The cost is the one a name was hiding: a front-end built to call its API on a fixed port (an entrypoint with alsoMatch) cannot be given that port by every universe, so such an app needs the address from <HOST>_URL instead.

Who can reach a universe

spec:
  expose: lan     # default
  # expose: local

lan publishes the proxy's ports on every interface and derives a publicly resolvable domain, so a phone or a colleague on the same network opens a universe with nothing to install. local publishes on 127.0.0.1 only and derives localhost: nothing is looked up anywhere and nothing off the machine can connect.

It is one setting and not two knobs because either half alone is a half-measure: a .localhost name with the proxy on 0.0.0.0 leaves the port open to anyone sending the right Host header, and a loopback bind with public hostnames still puts your naming in a stranger's DNS logs. doctor reports where the proxy actually listens and warns when that is not what the multiverse asks for.

What lan actually exposes

Worth reading once before choosing it. A development stack usually runs with debug pages on, seeded data and nothing in front of its mail catcher, so anyone on the network can read every message a universe sends, password resets included. Fine on a home network; not in a café, hotel or shared office.

Those hostnames are public DNS names pointing at a private address, so a web page you happen to open can make your browser send requests to a universe. Reading the answer needs permissive CORS, which development stacks often have. Under localhost the browser blocks that outright.

Why nothing publishes a port

Separate multiverse names, networks and volumes count for nothing while two universes map the same host port. So published ports are dropped — the ports: !reset [] above — and a universe is reached through the proxy. A service that genuinely needs its port back asks for it, in the manifest's publish: list or with a label:

services:
  db:
    labels:
      dev.multiversectl.publish: "true"

Only one universe can hold such a port at a time, which is the trade. ls -o wide has a PUBLISHED column, so you can see that the answer is none everywhere it should be.

Talking between services

Inside one app, services reach each other by compose service name on the app's own network — db, redis, mailpit — exactly as they would without multiversectl.

Between apps of a universe, use its hostnames through the proxy. One asymmetry under expose: local: a .localhost name resolves to the calling container's own loopback, not to the proxy, so container-to-container calls by hostname do not work. For both privacy and those calls, keep a resolvable domain and bind to loopback: domain: 127-0-0-1.traefik.me with expose: local is a name that only ever answers 127.0.0.1.

One proxy, several multiverses

The proxy belongs to the machine, so two multiverses wanting different entrypoints or a different expose compete for it: starting a universe in the second reconfigures it, and the first multiverse's universes stop answering until something is started there again. Starting says so:

! the shared proxy is being reconfigured: published on 127.0.0.1 instead of
  0.0.0.0, entrypoints web:80 instead of devapi:8001 web:80 — universes of any
  other multiverse on this machine stop answering until it is started from
  there again

Multiverses that run side by side want the same entrypoints and the same exposure.

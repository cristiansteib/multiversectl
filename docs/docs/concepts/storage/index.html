Storage and data

Where a universe's code, images, volumes and secrets live, which of them are shared, and what removing one destroys.

What a universe owns and what it shares

ThingPer universeShared
CheckoutsOne worktree per repositoryThe clone's git object store
ContainersOne compose project per appThe container runtime and its image cache
VolumesNamed after the app's multiverseNothing
NetworksOne or more per app, made by composeNothing: the proxy joins each app's own network
SecretsCopied into each checkoutThe originals in the clone
HostnamesOne per host keyThe domain and the proxy's ports

Both halves are the point: a universe is cheap because it reuses the expensive things, and those six per-universe items are exactly what collides when you run a stack twice.

Code: one clone, many worktrees

Each repository is cloned once under the multiverse root, and every universe gets a git worktree of that clone:

~/acme/
├── api/                  # the clone: history, remotes, objects
├── web/
└── universes/
    ├── 3/
    │   ├── api/          # a worktree on branch u3
    │   └── web/
    └── fix-login/
        ├── api/          # a worktree on branch fix/login
        └── web/

A worktree is a full checkout with its own index and branch, sharing the clone's objects: one fetch updates every universe's view of the remote, and a large history is stored once however many universes exist. They are ordinary directories — open one in your editor, commit and push from it.

Two worktrees cannot hold the same branch. That is git's rule. If --branch repo=main fails with "main is already used by worktree at …", the clone itself has main checked out. Pick another branch, or point that repository at a copy.

Data: a volume per app, per universe

Volumes are namespaced by compose project, and each app of each universe has its own. A database volume declared once becomes a different volume in every universe, with no change to the file:

$ docker volume ls | grep acme-u3
acme-u3-api_postgres_data
acme-u3-web_node_modules
$ docker volume ls | grep acme-fix-login
acme-fix-login-api_postgres_data   # a different database entirely
acme-fix-login-web_node_modules

Universe 3 can be migrated, seeded or dropped without touching fix/login. That is the main reason to run a second universe: a destructive migration on a review branch cannot reach what you were working on this morning. ls -o wide names the volumes, so you can check rather than trust:

$ multiversectl universe ls -o wide
...
on disk
REPO  WORKTREE                    PROJECT      VOLUMES
api   ~/acme/universes/3/api      acme-u3-api  acme-u3-api_postgres_data
web   ~/acme/universes/3/web      acme-u3-web  acme-u3-web_node_modules

Images and build cache

Images are not namespaced, deliberately: they are expensive to build and usually identical across universes, so two universes building the same Dockerfile reuse the layer cache.

The other side of that: an image tag is shared, so if two universes build the same tag from different code, the last build wins for whatever starts afterwards. Compose gives each multiverse its own build, so this bites mainly when a compose file pins an explicit image: name that it also builds — give such a service a tag containing ${UNIVERSE_SLUG}.

Secrets

Some files are deliberately not in git — a local .env, a service account key — so a worktree lacks them and the app half-starts with a confusing error. Name them and they are copied from the clone into every universe:

apps:
  - name: api
    repo: api
    secrets: [.env, service-account.json]

The clone is the source of truth: put the file there once and every universe gets it. An existing file in a universe is never overwritten, so one can diverge on purpose, and doctor fails when a file is missing from the clone.

When the repository ships a template, nothing has to be done. If the clone has no .env but a tracked .env.example, multiversectl does what a first run does: makes .env from the example, says so, and copies it in. Put your credentials in the clone's file once. universe up checks again before touching the proxy, so a file added later is picked up on the next start; one that is nowhere, with no example, stops the start and names each file and where it belongs.

The template is configurable. By default it is the secret's own name with .example added. Name another file, in the repository, with secretTemplates, or give "" to never make one, for a file that must come from somewhere else and should stop the start when it is missing:

secrets: [.env, service-account.json]
secretTemplates:
  .env: env.local                # made from env.local instead of .env.example
  service-account.json: ""       # never made: put the real one in the clone

Each key must be one of the app's secrets, and a template is a path inside the repository: the manifest is refused otherwise. Run with -v to see which file a secret was made from.

A copied file cannot see a universe's variables. A static list of origins in a committed .env is the same everywhere. For anything that depends on the universe — allowed hosts, trusted origins, CORS — use the dev.multiversectl.env.* labels, which win over env_file:.

Generated files

Two files appear in a universe's directory, both rewritten on every start and both safe to delete:

FileWhat it is
.multiverse-routes-<app>.ymlThe proxy labels, the dropped published ports, and the variables asked for by label.
.multiverse-overlay-<app>.ymlThe app's inline overlay: from the manifest, written out so the runtime can read it.

They sit beside the checkouts rather than inside them, so they never show up in git status.

What removing a universe destroys

rm is the one destructive command, so it prints what it will do and asks for the universe's name typed back:

  • Containers, networks and volumes of every app — gone, with the data in them.
  • Worktrees — gone. A worktree holding uncommitted work stops the removal until --force, and then it is lost.
  • The state file — gone.
  • Branches — kept, so committed work survives and a universe of the same name picks the branch up again.
  • The clones, the images, the proxy — untouched.

Use down when you only want the containers stopped: it keeps volumes and checkouts, so starting again is where you left off.

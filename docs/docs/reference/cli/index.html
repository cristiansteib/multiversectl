Commands

Every command, what it does and the arguments it takes.

Every command

Every command is a noun and then a verb: multiversectl universe up 3. Everything that acts on a universe lives under universe, which u shortens; the tree of multiverses and catalogs under catalog; what acts on the whole machine under system (the shared proxy, prune across every multiverse, the footprint of what this tool put on the disk, forget and reset); and the web view under server. init, start, status, doctor, schema, completion, self-update and version stay at the top level.

The same thing has the same word in every group, so one table is enough to guess a command:

ToThe wordFor example
run it, stop itup, downuniverse up 3, system proxy down, server up
listlsuniverse ls, catalog ls
say how one thing standsstatusserver status, system proxy status, status for the machine
make something newnewuniverse new, catalog new
put an existing thing inaddcatalog add acme/billing, universe notes add
take it outrmuniverse rm 3, catalog rm, agents skill rm
bring it up to datesyncuniverse sync 3, catalog sync

start is only the top-level command that installs, creates and runs in one step. The only short form is u for universe.

CommandWhat it doesExample
catalog ls [node-path]Show the catalog as a tree (a bare catalog shows its help), or the part under a node. Multiverses already installed are marked, and a layer that cannot be read is listed as unavailable with the reason. --fetch refreshes first, -o json is for scripts, --from shows another catalog. Install what it shows as not installed with multiversectl start <path> --install-only, where the path is the node's path in the tree (a catalog's path installs everything under it), or from a menu with catalog manage.multiversectl catalog ls acme/backend
catalog add <owner/repo | url | path>Put a multiverse in the catalog, in the place you pick: a repository with a catalog.yaml is linked as a catalog, one with only a multiverse.yaml as a multiverse; a local checkout is added by its origin; a manifest file goes into a repository (--same-repo, --repo, --new-repo). Where to put it is asked, with the repository each choice writes to; --at names it (a wrong or empty one lists the places), --yes means the root.multiversectl catalog add acme/multiverse
catalog rm <path>Remove an entry from the catalog that holds it. What it points at is untouched, and a multiverse installed from it stays installed.multiversectl catalog rm acme/billing
catalog manageThe catalog as a tree on one screen, for a person at a terminal. Move with the arrow keys; space installs what is not installed or uninstalls what is (on a catalog, everything under it), e leaves a node out on this machine or brings it back, r removes the entry from the catalog, a and u add an entry or update, / filters, ? lists every key. Installing, uninstalling and leaving out are staged, shown as you go, and made only when you press enter and review the list, which shows the command for each (start <path> --install-only, system forget <name>, catalog ignore <path>). Uninstalling only stops tracking it here: its files stay.multiversectl catalog manage
catalog ignore <path>...Leave a branch of the catalog tree out on this machine. An ignored catalog is not read, so one that is unreachable (behind a VPN, say) costs no wait, and what is under it is left out with it; an ignored multiverse is not offered for installing. A setting of this machine: nothing in any catalog repository changes. The tree marks it, and the web view has an Ignore button on each row.multiversectl catalog ignore acme/vpn-only
catalog unignore <path>...Bring ignored entries back: they are read and offered again.multiversectl catalog unignore acme/vpn-only
system footprintList everything multiversectl put on this machine and the command that removes each piece, in a safe order: the web server and proxy that may be running, every universe (with its containers, volumes and worktrees), the clones of your repositories, branches left behind, the configuration and caches, shell completions, and the programs. Anything that would lose work that exists nowhere else, such as uncommitted changes, commits on no remote or a volume's data, is marked. It removes nothing. --script prints only the commands; -o json is for scripts. Run it before system reset, which makes multiverses unknown to it.multiversectl system footprint
system forget <multiverse>Stop tracking a multiverse on this machine; its files stay on disk. Takes the name or the catalog path.multiversectl system forget billing
system resetForget this machine's root catalog and every installed multiverse, to start again from another root. Lists them and asks; deletes no file, checkout or universe. Warns about multiverses that still have universes.multiversectl system reset
catalog new [dir | name]Make a multiverse or a catalog and list it; it asks which (--type multiverse|catalog). For a multiverse it guides the setup: choose its repositories (the checkouts beside it, a search through your GitHub or GitLab repositories, or pasted URLs), where its own repository lives (a new private one under any account you can create in, an existing one, or only here), where to list it in your catalog, and whether to start it. Writes multiverse.yaml and an AGENTS.md describing the multiverse and the tool, commits and pushes after you confirm. For a catalog the argument is its name: a file in its parent's repository (--same-repo), an existing repository (--url) or a new private one (--create). Flags answer every question: --name, --repo [name=]url (repeatable; name= sets the name it has in the manifest), --scan, --create owner/name (or a full URL) with --provider github|gitlab and --host for a self-hosted instance, --url, --local, --public, --at, --no-link, --no-install, --yes.multiversectl catalog new --scan --create acme-org/multiverse
catalog sync [multiverse ...]Fetch the catalogs, fast-forward each multiverse's manifest from where it was installed, and clone the repositories the new manifest lists (up to four at a time, with a line of progress for each). Refuses a manifest with local changes. It also fast-forwards the shared clones (what secrets are made from), leaving one with changes, on another branch or ahead of origin alone and saying why.multiversectl catalog sync
schema [field path]Print what a multiverse.yaml takes, field by field, from the schema this binary was built with — no repository and no network. A path is a field's dotted name, stepping through a list as if it were one item (spec.apps.hosts.port). The field named is spelled out one level down and anything deeper is listed by name under fields, because the whole schema is some 130 KB — a key of its own, since a properties holding names would be an invalid schema that still looked like one. --depth expands more; --depth=-1 is the schema itself. --kind catalog is the other file's fields; --json prints the same as JSON.multiversectl schema spec.apps
universe new [number|name]Create a universe on a branch: one worktree per repo, secrets and state. In every repository the branch — the universe's name, or --branch — is checked out where it already exists (in the clone or on origin, tracking origin when it is only there), and started from the base where it does not; what each repository got is said. So a branch to review or carry on is universe new <branch> too. A branch already checked out in another universe or in the clone is refused, because git allows a branch in one worktree only, and the place is shown. With no name the next free number is used, stepping over a number whose branch a removed universe left. --branch (repeatable) is a bare name for every repo or repo=name for one; --base is where a new branch starts, the same way. --about records what it is for. Removing the universe deletes only the branches it started.multiversectl universe new fix/login
universe up <universe> [app ...]Start a universe, all apps or only those named; an app with autostart: false starts only when named. --with adds optional service groups. An app that does not start does not keep the others from it: the rest are started, a summary at the end says which apps are up and which failed and why, and the exit status is non-zero. The hooks of a failed app do not run, those of the apps that started do, and the multiverse's own postUp hooks wait until none failed. --fail-fast stops at the first failure instead. After an app's services start it waits until the ones with a healthcheck are healthy and the hosts that set ready answer, before its postUp hooks: --no-wait skips that, --wait-timeout 10m sets how long (default 5m; running out is a warning), --wait-strict makes running out an error. --rebind-proxy lets the start reconfigure the shared proxy (the interface it is published on, its entrypoints, its TLS) when it differs and universes of other multiverses are running; without it that is refused. All of these are on start too.multiversectl universe up 3 api --with workers
universe down <universe> [app ...]Stop a universe; keeps data and checkouts.multiversectl universe down 3
universe about <universe> [text] [--pr url]Everything about one universe, read from disk: what it is for and its pull or merge request, which manifest it uses, whether that loads (every problem is listed), when the universe was last started, by which build and whether the manifest was edited since, and the hooks the manifest ties to its life — the event, where each runs, whether a once-only one has run and what a failure means. With text or --pr it sets what the universe is for, kept with it and shown by ls, -o json and the web page, so a person or another agent finding it later knows what it is doing; --clear empties both, and universe new --about sets the text when it is made. --diff shows how the manifest changed since the universe started, --manifest prints it as it is now, and --files prints the files its render entries make, as universe up writes them, without writing anything: how a template is tried. Starting a universe records a fingerprint of the manifest and keeps a copy beside its state, because the file can be edited afterwards and the universe goes on running on what it started with; one started before that was kept says so.multiversectl universe about 3 "fixing the login redirect" --pr https://github.com/acme/api/pull/42
universe notes <universe> [add|set|rm]Short messages a universe keeps for the user and other agents: a line or two the next reader needs — what is blocked, what is asked of someone, a decision, where things stand — rather than an account of the work, which the commits already are. Reading another universe's notes, or adding one to it, is how agents in different universes reach each other. notes <universe> reads them, add appends one, set replaces what one says and rm takes one out; the id (n1, n2, …) and the time are the tool's to fill in, and --by says who is speaking. Each note is a file of its own, under .multiverse/notes/ inside the universe, so several agents writing at once cannot clash, and one can be added while the universe is being started. A removed note's id is never reused. - as the text reads it from standard input. about is the single line saying what the universe is for. The universe page shows the same notes, and removing the universe removes them.multiversectl universe notes add 3 --by claude "blocked: needs SMTP creds in .env"
help [command] [--tree] [--flat]Help about one command; with --tree, every command, nested under the one it belongs to, with the aliases each answers to in brackets and a line on what it does. It reads the commands this binary has, so it cannot disagree with it. --flat (which implies --tree) prints one full command per line, to grep.multiversectl help --tree
start [name] [source]From nothing to something running: installs the source, picks the universe — the one named with -u, the only one there is, or a new one — creates it if it has to, starts it, and prints its addresses. A source is read in this order, and what it was taken for is said: a node in your catalog, a path, a git URL, then owner/repo. A repository may define any number of multiverses: every .yaml or .yml file in it that says kind: Multiverse is one, wherever it is and whatever it is called. start billing owner/repo (or owner/repo:billing) picks one by its metadata.name; a repository with a catalog is read as one, so no root catalog is needed. A repository that defines no multiverse but has a compose file runs as itself, named after the repository (with its owner in front if that name is taken; --as names it). A multiverse already installed is used as it is. With no source it uses the one -m names or the folder you are in, else you pick from your catalog. Where it goes is asked, with ~/multiverse/<name> prefilled, unless --root, --base or --yes say. --open opens the first address. Before anything is cloned it checks the machine and says what to run for each problem: docker reachable; compose and buildx present, with their versions; free disk space (refused under 2 GiB); each repository of the multiverse that is not cloned yet is readable (git ls-remote, 15 seconds each, telling no network from no access from an unknown ssh host key); and the secret files the manifest and the compose files (secrets: file:) name are there. A failure stops the start; --skip-preflight starts anyway. The multiverse's own repository is fetched before its list of repositories is known, so it is the one thing checked by the install itself. Several universes and no -u is a question at a terminal and an error in a script. A catalog node installs every multiverse under it: --install-only stops after installing, and --exclude <path> (repeatable) leaves out a multiverse or a whole branch. A catalog repository that does not answer within 20 seconds (MULTIVERSECTL_CATALOG_TIMEOUT) is shown as unavailable, and the rest of the tree stays usable; one fetched before is read from its last copy and marked as not refreshed. Catalogs are read at the same time, and the web view shows each one's state as it answers.multiversectl start acme/multiverse
universe sync [universe]Bring a universe's code up to date. A universe's checkouts keep the commit they were made from, so a fix that reached main afterwards is not in them. sync fetches and moves each checkout forward when that loses nothing, saying what it did per repository. A checkout with uncommitted changes is never touched; one with commits of its own is left alone unless --merge merges the branch in. --all does every universe. It re-reads the compose labels, so addresses follow; restart the universe to run the new code. universe ls -o wide and -o list say which checkouts are behind.multiversectl universe sync 1
universe rm <universe>Destroy a universe: worktrees, containers, volumes and state. Uncommitted work in a worktree stops it until --force. Asks first; deletes the branches it started when every commit is elsewhere, and keeps one holding unpushed work; --yes skips.multiversectl universe rm 3 --yes
universe lsList universes under a header naming the multiverse, its root, its multiverse.yaml, where it came from and the universes folder. Then a table per universe: a row per address with its app and branch, the forwarded address beside it when there is one, and a row for each repository checked out with no services. -o wide is everything else — the service behind each address, what is on, what is off and why, the host ports it publishes — and an on disk block of worktrees, compose projects and volumes. -o json is a compact one-line document for a script or an agent, -o json,wide the whole detail, -o list one line per universe; they combine with commas. universe ls <universe> shows one. The line of -o list says whether the universe is running, partial, stopped or only created, how many of its services are up, when it was last started, its branches and what it is for. A universe is partial when some of the services it expects are not running, and a line under the table says which and why: stopped (exited cleanly), failed (exited with an error, is restarting or dead; with the runtime's own words) or not started. Only what should be up is expected: an app on demand while none of it runs, an app whose repository has no compose file (no runtime), and a service that is optional, deselected or behind a profile are not counted, and the line names the apps it left out. -o json carries the same as why and skipped.multiversectl universe ls -o wide
universe urls <universe>Print a universe's URLs, one per line.multiversectl universe urls 3
server up|down|restart|status|open|pairRun the web view in the background, end it, restart it on the installed build (same options, same link), say where it is, or open it in the browser (starting it first if needed). The view is the separate multiversectl-server program, found beside this one or on the PATH; it is live and can start, stop, create and remove universes, and opens from a link carrying a token that up and status print. up takes --addr (port 0 picks a free one, and a port another process holds is replaced by the next free one), --open, --read-only and --expose (listen on every interface, for another machine on the network). pair gives that machine a six-digit code to open the page with instead of the link: one machine, once, five minutes.multiversectl server up --open
system pruneRemove universes across every installed multiverse (-m narrows it to one), the way universe rm does. It lists what it will do and keeps, saying why, those with containers running (--all includes them) and those with uncommitted work in a worktree (--force discards it). It asks first; --yes skips the question and --dry-run shows the list and stops. The shared clones, the proxy and the installed multiverses are left alone, and a branch a universe started is deleted only when every commit on it is elsewhere.multiversectl system prune --all --yes
statusWhat is on this machine and what runs, and no judgement of it: the root catalog, the shared proxy and its entrypoints, the web view and its link, then each installed multiverse — where it came from and whether its manifest is behind that — with one line per universe: running, partial, stopped or only created, how many of its services are up, when it was last started, its branch and what it is for. Offline and quick; --fetch compares each manifest with its remote first; -o json is for scripts. doctor checks it all and says what to fix.multiversectl status
doctor [universe]Check this machine, as a list of checks under three headings. This machine: the root catalog (whether it is readable and has a remote), the container runtime and Docker's free networks, git, the shared proxy and where it listens, and the web view. Then each installed multiverse: whether its manifest is behind upstream, whether its shared clones are, a proxy it would clash with, that its domain resolves to this machine, and that its git host is signed in, with how many universes it has and how many run. Name a universe and it is checked too: its secrets, each app, and every address of a running app, asked once (any answer below 500 counts; the proxy's own 404, a refused connection or a 5xx on the front page are warnings). Each line is ✓, ! for a warning, ✗ for a failure, or ○ for something that is simply not running; under each heading, → is the command that puts its warnings right, once however many it fixes. It exits 1 when a check fails. Offline and quick; --fetch compares with the remotes and looks for a newer release; -o json gives every check with its fix. --preflight asks instead what a first start would need, with no universe and nothing cloned: docker reachable, compose and buildx present, free disk space, and, when a multiverse is installed, that each of its repositories can be read and its secret files are there.multiversectl doctor 3
universe exec <universe> <app> -- <cmd>Run a command in a running container of a universe. --service picks one when the app has several. Streams straight to your terminal.multiversectl universe exec 3 api --service db -- psql -U postgres
universe run <universe> <app> -- <cmd>, universe run <universe> --hook <event> [app...]Run a command in a fresh one-off container instead, for a task that should not need the service up — a migration, a shell on a stopped app. With --hook it runs the hooks the manifest ties to an event (postCreate, preUp, postUp, preDown, postDown, preRemove) now, for the apps named or for the multiverse and every app: how a hook that was warned about is run again, and how one is tried before a start depends on it. A once-only hook runs again and is not marked; a failure is an error.multiversectl universe run 3 --hook postUp api
universe env <universe>Print a universe's environment as export lines for your shell.eval "$(multiversectl universe env 3)"
system proxy up|down|statusStart, stop, or inspect the shared proxy and its network. Universes keep their data when it stops.multiversectl system proxy status
init [owner/repo | url | path]Set up this machine's root catalog. It says what the machine already has, offers to keep it, and checks it is a Catalog and tagged with the topic multiversectl-catalog. On a machine with nothing it searches your GitHub and GitLab repositories for a tagged root, or takes an existing repository or path, a new private repository (--create, under any account you choose) or a local git repository (--local). It refuses to switch roots while multiverses installed from the current one exist; system reset first.multiversectl init --create multiverse-index
self-updateReplace this binary, and the web view beside it, with the latest release, and restart the web view if it is running. A release is published only once its binaries are attached, but a tag can still be ahead of them for a moment: when the newest version has none to download yet, it says version X has no binaries attached yet instead of reporting that it is up to date, and a release that has no binary for this platform says so. Commands run in a terminal end with a line on stderr when a newer release is out, with how many fixes it brings; the look is made in the background at most every 30 minutes, so it shows from the second command on. MULTIVERSECTL_NO_UPDATE_CHECK=1 turns it off. The web view shows the same as a banner.multiversectl self-update
versionPrint version, commit, build date and Go version.multiversectl version
agents skill install|rm|status|showinstall writes a short skill for Claude Code to ~/.claude/skills/multiversectl/SKILL.md (--here for this folder's .claude/skills, --dir for another). It tells an agent how to discover the tool (--json), to work in a universe of its own and leave a note and PR on it, and what to ask about first: other universes, prune, system reset, secrets, the shared proxy. The file records the version that wrote it and any newer multiversectl rewrites its own copies, so an upgrade never leaves an agent on old advice; a file it did not write is never touched. status says where it is and whether it is current, show prints it, rm removes the copy it wrote.multiversectl agents skill install
completion [shell]Install shell completions for bash, zsh or fish under your home directory, after asking (--yes skips; --shell overrides $SHELL; --uninstall removes them). With a shell's name, including powershell, prints the script instead. An installed script records the version that wrote it, and any later run of multiversectl rewrites it when the version has changed. Multiverse names and catalog paths complete from what is already on this machine, with no network.multiversectl completion --yes

In --help the commands are grouped: universe management, tool initialization, and catalog management. Run with no command, multiversectl shows the help and, on a machine with nothing installed, the two ways to begin.

Global flags: -f, --manifest path to the manifest; -m, --multiverse which installed multiverse to act on (default: the one whose folder you are in, else the only one installed); --root multiverse root (default $MULTIVERSECTL_ROOT, the manifest's spec.root, the saved config, or the manifest's directory); --no-color; -v, --verbose says what is being done (-v the steps and what the commands print, -vv the commands run, -vvv how each ended); --json machine-readable output on any command (--less for the least, --full with --help for every command) (see agents). <universe> is a positive integer. --state-dir <dir> (or $MULTIVERSECTL_STATE_DIR) keeps every per-user file under that directory instead of your home: the configuration, the catalog and update caches, the web view's token and state, the shared proxy's compose file (under a project name of its own, so a rehearsal cannot recreate the proxy your universes use), the shell completion and agent skill files, and the default place multiverses are installed (<dir>/home/multiverse). It is how a first run is rehearsed on a machine that has already been used. What it starts lives outside the directory, in Docker: undo it with the same flag, multiversectl --state-dir <dir> universe rm <universe> for each universe and multiversectl --state-dir <dir> system proxy down, then delete the directory. Its proxy needs the same ports as your real one, so only one of the two runs at a time: stop the real one first (multiversectl system proxy down), and start it again after.

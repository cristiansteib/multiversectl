What's on your machine

One picture of it all: what the machine keeps and every universe shares, what one universe owns, and what is rewritten on every start — with networking, data and what is actually running.

Three kinds of thing

Everything multiversectl touches is one of three things: something the machine keeps and every universe shares, something one universe owns, or something written again from scratch on every start. Tell them apart and the rest of the tool follows.

What survives what

down takes the containers away and leaves everything you would mind losing. rm is the one destructive command, which is why it asks for the universe's name typed back.

ThingWhere it livesAfter downAfter rm
Branches and commitsThe clonekeptkept
The clone and its git objects<root>/<repo>/keptkept
Images and the build cacheThe daemon, not namespacedkeptkept
The shared proxyIts own compose projectkeptkept
Worktrees, with your uncommitted edits<root>/universes/<universe>/<repo>/keptgone
Volumes, with your dataThe daemon, named per app per universekeptgone
The state file, with its hostnames and chosen ports<root>/universes/<universe>/universe.yamlkeptgone
ContainersThe daemon, one compose project per appremovedgone
App networksThe daemon, made by composeremovedgone
The generated fragmentsBeside the checkoutsleft, rewritten next startgone

So down then up puts you back where you were, data included. Life of a universe walks the same ground command by command, and Storage and data is the long version.

Networking, in one picture

No universe publishes a host port — two copies of one stack cannot both have port 8000, and the first collision would make all the other namespacing pointless. Instead one proxy holds one set of ports for the whole machine and tells the universes apart by the hostname in the request.

Inside one app, services reach each other by their compose service name — db, redis, mailpit — exactly as they would without multiversectl, because that network belongs to that app of that universe alone. That is why the names do not clash: universe 4's db is on a different network, and neither app can see it.

Between apps of one universe, call them by their hostnames through the proxy. The whole story — entrypoints, domains, who can reach a universe, and serving https — is in Networking.

Data: whose is whose

Volumes are namespaced by compose project, so a database volume declared once in your compose file becomes a different volume in every universe, with no change to the file:

$ docker volume ls | grep acme
acme-u3-api_postgres_data          # universe 3's database
acme-u3-web_node_modules
acme-fix-login-api_postgres_data   # a different database entirely
acme-fix-login-web_node_modules

That is the main reason to run a second universe: a destructive migration on a review branch cannot reach what you were working on this morning. Images are the deliberate exception — they are expensive and usually identical, so universes share them and the layer cache.

Your code works the same way: one clone per repository holds the history, and each universe gets a git worktree of it on its own branch. A large history is stored once however many universes exist, and one fetch updates every universe's view of the remote.

Storage and data covers secrets, the generated files and exactly what rm destroys.

What is actually running

One container per service per app per universe, plus one proxy for the machine. Nothing else: multiversectl has no daemon or agent of its own, and nothing of it is running between commands.

$ docker ps --format '{{.Names}}'
multiverse-proxy-traefik-1   # one for the machine
acme-u3-api-web-1            # universe 3, app api, service web
acme-u3-api-db-1
acme-u3-web-app-dev-1
acme-u4-api-web-1            # universe 4, the same services again
acme-u4-api-db-1
acme-u4-web-app-dev-1

The name is the whole hierarchy: multiverse, universe, app, service. It is what keeps two repositories that both call a service app from meeting, and it is how every command finds what belongs to what.

The cost of a universe is therefore the cost of its containers' memory. That is the real limit on how many you run at once, and it is why down exists: a universe that is down costs disk, not memory, and comes back where it left off.

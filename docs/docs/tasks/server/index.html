Explore and run it in a browser

A live web view of the catalog, the multiverses and the fleet of universes, with versions and buttons to start, stop, create and remove universes, behind a token.

See the whole setup in a page

One command opens a page that shows every universe on the machine, what is running in it, and what its code has become. It is live: start a universe in a terminal and the page knows.

$ multiversectl server up --open
✓ serving http://127.0.0.1:7777/?t=… in the background (pid 4242); stop it with: multiversectl server down
  • One card per universe: its branch, its apps, the state of every service, and its addresses as links you can open.
  • What the code has become: for each repository, what its branch adds to the one it is to be merged into — 12 files changed against main +248 −96 — what is not pushed, not committed or behind, and its pull or merge request with GitHub's mark for open, draft, merged or closed. A universe in view is read again every minute, and its remotes are asked every five (never with a prompt: a remote that wants a password is skipped); Reread asks them at once, and the card says how long ago they were asked.
  • A page for each universe: Open on a card, or a change in its code, goes to the universe's own page. A tab per repository, and in it a tab for what the branch changed and one for what is not committed, with the change read the way a review is: a Commits tab (newest first; a commit with a body opens to show it) and a Files changed tab, the files as a tree beside one diff at a time. Picking a file swaps the diff in place, under a bar that stays in sight with its path, buttons to copy the path or the full path, and the previous and next file. A branch whose work its base holds already reads as landed, however it got there: its lines are the record of what was merged rather than work waiting to be done, and it gives up its place at the front of the tabs. Under its apps, the overview shows the universe's notes, the short messages people and agents leave each other, and takes a new one; the address says which change is open, so you can send it.
  • Start, stop, update, create and remove, with what docker compose prints streaming into the page.
  • The rest of the setup: the catalog you install multiverses from, where each has drifted, and the versions of git, docker and the tools on this machine.

Open one up

Details opens a panel on a universe: every container, what it is using, and the address that reaches it. Logs reads a service's log as docker logs would — following as it arrives, filtered to the lines you are after, errors and warnings marked. Colours a program wrote come through, so its output reads as it does in a terminal. Wide gives it the whole window.

Restart restarts a service in place, after a second press to confirm. Everything else in the panel only reads.

Watch what it is using

Stats draws processor time and memory for every running container, by universe, by app or one line each — which is how you find the universe that is eating the laptop. Pick the universes to draw, or slow the reading down. The history is the page's own: it starts when you open it.

Act from the page

A multiverse has New universe, Update and Make current; a universe has Start, Stop, Remove… and, when its code is behind, Update code. Each is the use case the command line runs, started in the background; a universe runs one operation at a time, and different universes run side by side.

That holds across programs, not only within the page: the page, a terminal and an agent are separate processes, and each takes a lock in the multiverse before it changes anything. A second one is told what has it — universe 2 is busy: pid 4242: multiversectl universe up 2 is working on it — rather than running alongside. Creating and removing take a lock on the multiverse itself, since they change which universes there are; everything else locks only the universe it works on.

Removing is the one that cannot be undone, so it is slower on purpose: the dialog asks for the universe's name, and uncommitted work stops it until a second press says to discard it. --read-only removes every button and makes the server refuse every action.

Running it

server up runs it detached, so closing the terminal does not stop it; server status says where it is, server down ends it. Its output goes to server.log beside the configuration, which is where start explains itself when it cannot start. To keep it in a terminal, run multiversectl-server.

An update replaces the program on disk but not the one running, so self-update and the install script restart it, and after a package upgrade server status says it is on the older build. server restart brings it back with the address and flags it had, link unchanged. The flags are in the command reference.

Open it on another machine

Start it with --expose and it listens on every interface, so a laptop on the same network can watch what the desktop is running. The link is 192 bits of base64, which nobody is going to read across a desk, so ask the running server for a code instead:

$ multiversectl server pair
✓ code 418 902 — type it into the page on the other machine
  open http://192.168.1.23:7777/
ℹ it opens one machine, once, and runs out in 5 minutes

The other machine opens that address, types the code, and has what this machine has. The code opens one machine, is spent by the first use, dies after five wrong guesses and is forgotten after five minutes — and nothing hands one out but a request that already has the link. An agent asked for access runs the same command and reads out what it printed.

The page is served over plain HTTP, so keep --expose to a network you trust; --read-only is there for a machine you only want to be watched from.

Let a coding agent work with it

An agent needs no server and no protocol: it runs the command line, and -o json gives it what it needs in few tokens. Each universe is its own folder and its own set of containers, so several agents can each work in one at the same time.

$ multiversectl universe ls -o json
{"multiverse":{"name":"acme","root":"/home/me/acme","manifest":"…/multiverse.yaml","universesDir":"…/universes","clones":{"api":"…/api"}},
 "universes":[{"name":"3","state":"running","up":"3/3","dir":"…/universes/3",
   "checkout":{"api":"…/universes/3/api"},"branch":{"api":"u3"},"urls":{"api/api":"https://api-3.example.test"},
   "containers":{"api/web":"acme-u3-api-web-1"}}]}

One line, and only what an agent acts on: where the multiverse and its clones are, and per universe whether it runs, every repository's folder, the branches, the addresses under urls named by app and host, and under containers the running container of each service. Services that should be up and are not are listed under down.

--json works on every command, -o json,less is the least per universe and -o json,wide everything. multiversectl agents skill install teaches Claude Code all of it once.

Who can use it

A page that can remove a universe must not be open to whoever reaches the port. The server makes up a token on first start, keeps it in server.token beside the configuration (readable by you only), and the link trades it for a cookie it then drops from the address bar. Without that cookie every request is refused, the websocket included.

It also listens on loopback and answers only requests addressed to localhost, so a page on another site cannot point a name it controls at your machine and talk to it through your browser. Anything that changes state needs a header only the page sends. --expose lifts the address restriction; the token still applies.

The page loads nothing from outside, which its content security policy enforces, and builds everything from text, so a branch name or a note cannot inject markup.

Manage many multiverses from one index

Set up a root catalog, nest another one under it, list multiverses in it, and install only the ones this machine needs.

Use a multiverse someone points you at

$ multiversectl start acme/multiverse

That is the whole of it on a machine with nothing set up: it installs the multiverse, makes universe 1 and starts it. The source can be owner/repo (GitHub), any git URL, or a path. A repository holding a catalog.yaml is read as a catalog; otherwise it is read for the multiverses it defines (every .yaml or .yml file in it that says kind: Multiverse, whatever it is called and wherever it is), and start says which it took. When a repository defines several, name the one you want, start billing acme/platform or acme/platform:billing; without a name you are asked, and in a script the error lists the names.

$ multiversectl start billing acme/platform

Keep your own index

# searches GitHub and GitLab for your root, or asks
$ multiversectl init
# or say where it goes
$ multiversectl init --create multiverse-index
$ multiversectl init me/multiverse-index
$ multiversectl init --local ~/multiverse-index

--create makes the repository through gh, private unless you add --public. Without gh, make it yourself and pass it. A repository that already holds a catalog.yaml is used as it is. Creating and pushing ask first; --yes accepts for scripts. A root that lives only here works, and status keeps saying nobody else can use it.

On a fresh machine init looks for a repository tagged multiversectl-catalog on the services you are signed in to and offers those first. On a machine already set up it says what the root is and what is installed from it.

Moving to another root is refused while multiverses from the current one are installed. multiversectl system reset forgets the root and the installed multiverses without deleting a file, checkout or universe; system prune first if you want those gone too.

Start again on a new machine

$ gh auth login                      # or let init sign you in
$ multiversectl init                  # finds your root
$ multiversectl start                 # pick what this machine needs

That restores what git holds: the multiverses, their manifests and every repository. It does not restore what git never had — the files a multiverse keeps out of it (.env, service-account keys, listed under secrets and copied from its clones), uncommitted work, unpushed branches and database volumes. Keep those somewhere of your own before wiping a machine.

Put a multiverse in the right place

$ multiversectl catalog add acme/billing
› acme/billing holds a multiverse manifest (billing)
┃ Where should it go?
┃   index (root)         writes to github:me/multiverse-index
┃   ├─ personal          writes to github:me/multiverse-index
┃   └─ acme              writes to github:acme/index · another repository
┃ ❯    ├─ backend        writes to github:acme/index · another repository
┃      └─ frontend       writes to github:acme/index · another repository
┃      secret-team       no access or not found: github:acme/secret-index
↑ up • ↓ down • / filter • enter submit

Anything a command needs and was not given is asked for like this: ↑ ↓ to move, Space to tick, / to filter, Enter to accept, Esc to stop. universe up offers your universes, system forget your multiverses, universe new the next free number. Without a terminal nothing is asked and the command says what it wanted.

The default place is the deepest catalog in a repository with the same owner as the multiverse, otherwise the root. --at <path> names it (/ is the root); with --yes and no --at the entry goes to the root, never into a repository nobody named. A --at that names no catalog lists the places instead.

The source can be a repository, a local checkout (added by its origin, so other machines can fetch it), or a manifest file. A file has no repository, so it needs one — a copy in the catalog's own, or one of its own:

$ multiversectl catalog add ./acme.yaml --new-repo acme-org/multiverse

Writes go to the file that owns the place you chose, are committed, and are pushed after one confirmation, taken before anything is written. A rejected push is reported and leaves your copy clean. catalog new --type catalog makes an empty catalog to group under.

catalog rm <path> removes an entry and touches nothing it pointed at, but it is a commit on a branch other people update from, so it says what will happen before it asks, and a bare Enter is no:

$ multiversectl catalog rm acme/backend
› remove acme/backend from the catalog
›   removes: the entry acme/backend (a catalog), and with it everything listed under it — 3 multiverses: acme/backend/billing, acme/backend/auth, acme/backend/mail
›   leaves alone: the catalog file and the repositories it points at; only the link to them goes
›   installed here from it, and staying installed: billing
›   it is committed and pushed straight to main of github:acme/index, not through a pull request, so everyone who updates their catalog sees it gone; `git revert` on that commit brings it back
? remove acme/backend from the catalog: commit and push to github:acme/index (main)? (y/N)

Where nothing can bring it back — a catalog file that is not in a git repository — it says that instead of promising a revert. Without a terminal it stops after saying so, until --yes.

Start what this machine needs

# a multiverse, or everything under a catalog
$ multiversectl start acme/backend/billing
# no source: the one you are in, or pick from your catalog
$ multiversectl start
$ multiversectl status

A multiverse goes in ~/multiverse/<name>, offered prefilled so Enter accepts it. --root (that folder), --base (the folder above it), $MULTIVERSECTL_ROOT or --yes settle it without asking, and a --root that already holds the checkouts reuses them. There is no "current" multiverse to switch: a command acts on the one named with -m, else the one whose folder you are in, else the only one installed, and says which when it cannot tell. Installing never writes to a catalog.

Keep installed multiverses current

$ multiversectl status --fetch
MULTIVERSE  FROM             STATE
acme        acme/multiverse  manifest behind 1 · billing-api not cloned
› next: multiversectl catalog update acme
$ multiversectl catalog update
✓ billing-api: cloned
✓ acme: manifest moved forward 1 · billing-api cloned

status compares each multiverse with where it came from, offline unless you pass --fetch. catalog update fetches, moves each manifest forward and clones what the new one lists; it refuses a manifest with local changes and leaves a pinned one alone. system forget <name> stops tracking a multiverse and leaves its files.

Hearing about changes while you work

Nothing updates by itself; you are told. Every command under universe opens with a line when the manifest has moved upstream, as does status. To have that news be current, a command looks at the remote when the last look is over six hours old, for at most four seconds, silently if it fails. MULTIVERSECTL_NO_FETCH=1 turns it off.

$ multiversectl universe ls
! acme: 2 upstream changes to its manifest: multiversectl catalog update acme

Editing the manifest here

A manifest installed from a repository is a checkout under <root>/.multiverse/source. Edit it there and keep working: catalog update never overwrites an edit, and status says what it found.

  • Edited, nothing upstream: manifest edited here. A choice, not news.
  • Edited, and upstream moved: manifest edited here · manifest behind 2 — keep working, or stash, catalog update, git stash pop.
  • Committed here, and upstream moved: manifest diverged (1 local, 2 upstream). catalog update cannot fast-forward; git pull --rebase in that folder.

A multiverse installed from a file has nothing to compare with and is never updated.

Make a multiverse others can join

# in an empty directory, or a checkout of the repository you made for it
$ multiversectl catalog new

It first asks what to make: a multiverse, or a catalog to group them (--type skips the question). For a multiverse the guide asks in turn and shows the plan before creating or pushing anything:

  • Its repositories. The checkouts already beside the directory (each origin becomes its URL), a search through your repositories on GitHub or GitLab, or URLs you paste. Mix them as you like.
  • Its name. What most repository names start with — acme-api and acme-ui make acme, and shorten their keys to api and ui.
  • Where its own repository lives. A new private one under any account you can create in, one that exists, the directory's own origin, or only this machine.
  • Where to list it in your root catalog, and whether to start it here so the next command can be universe new 1.

It writes multiverse.yaml and a short AGENTS.md, commits and pushes. That AGENTS.md tells a person or a coding agent what the repository is and how to run universes of it; one already there is left alone. A repository with a docker-compose.yml becomes an app of the same name; one without is only checked out.

$ multiversectl catalog new ~/acme/multiverse --scan --create acme-org/multiverse --yes
$ multiversectl catalog new --name acme --repo acme-org/api --repo https://gitlab.com/acme/web.git --local
$ multiversectl catalog new backend --type catalog --same-repo --at /

The repository it makes holds only the definition. Nothing needs to list it for others to use it: anyone can run multiversectl start acme-org/multiverse, and a catalog entry is only a shortcut to it. Leave machine-specific lines such as an absolute spec.root out of a manifest you share: start picks where it goes.

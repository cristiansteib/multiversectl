Manage many projects from one index

Set up a root catalog, nest another one under it, list projects in it, and install only the ones this machine needs.

Use a project someone points you at

$ multiversectl project install acme/multiverse
$ multiversectl universe new 1
$ multiversectl universe up 1

That is the whole of it on a machine with nothing set up. The source can be owner/repo (GitHub), any git URL, or a path. A repository holding a catalog.yaml is read as a catalog, one with only a multiverse.yaml as a project; install says which it took.

Keep your own index

# searches GitHub and GitLab for your root, or asks
$ multiversectl init
# or say where it goes
$ multiversectl init --create multiverse-index
$ multiversectl init me/multiverse-index
$ multiversectl init --local ~/multiverse-index

--create makes the repository through gh, private unless you add --public. Without gh, make it yourself and pass it. A repository that already holds a catalog.yaml is used as it is. Creating and pushing ask first; --yes accepts for scripts. A root that lives only here works, and status keeps saying nobody else can use it.

On a fresh machine init looks for a repository tagged multiversectl-root on the services you are signed in to and offers those first. On a machine already set up it says what the root is and what is installed from it, and tags the repository if an older root was never marked.

Moving to another root is refused while projects from the current one are installed. multiversectl reset forgets the root and the installed projects without deleting a file, checkout or universe; system prune first if you want those gone too.

Start again on a new machine

$ gh auth login                      # or let init sign you in
$ multiversectl init                  # finds your root
$ multiversectl project install        # pick what this machine needs
$ multiversectl universe new 1

That restores what git holds: the projects, their manifests and every repository. It does not restore what git never had — the files a project keeps out of it (.env, service-account keys, listed under secrets and copied from its clones), uncommitted work, unpushed branches and database volumes. Keep those somewhere of your own before wiping a machine.

Put a project in the right place

$ multiversectl catalog add acme/billing
› acme/billing holds a project manifest (billing)
┃ Where should it go?
┃   index (root)         writes to github:me/multiverse-index
┃   ├─ personal          writes to github:me/multiverse-index
┃   └─ acme              writes to github:acme/index · another repository
┃ ❯    ├─ backend        writes to github:acme/index · another repository
┃      └─ frontend       writes to github:acme/index · another repository
┃      secret-team       no access or not found: github:acme/secret-index
↑ up • ↓ down • / filter • enter submit

Anything a command needs and was not given is asked for like this: ↑ ↓ to move, Space to tick, / to filter, Enter to accept, Esc to stop. universe up offers your universes, project use your projects, universe new the next free number. Without a terminal nothing is asked and the command says what it wanted.

The default place is the deepest catalog in a repository with the same owner as the project, otherwise the root. --at <path> names it (/ is the root); with --yes and no --at the entry goes to the root, never into a repository nobody named. A --at that names no catalog lists the places instead.

The source can be a repository, a local checkout (added by its origin, so other machines can fetch it), or a manifest file. A file has no repository, so it needs one — a copy in the catalog's own, or one of its own:

$ multiversectl catalog add ./acme.yaml --new-repo acme-org/multiverse

Writes go to the file that owns the place you chose, are committed, and are pushed after one confirmation, taken before anything is written. A rejected push is reported and leaves your copy clean. catalog create <name> makes an empty catalog to group under; catalog rm <path> removes an entry and touches nothing it pointed at.

Install what this machine needs

# a project, or everything under a catalog
$ multiversectl project install acme/backend/billing
$ multiversectl project install acme personal/notes
# no source: pick from your catalog, installed ones marked
$ multiversectl project install
$ multiversectl project status
$ multiversectl project use billing

A project goes in ~/multiverse/<name>, offered prefilled so Enter accepts it. --root (that folder), --base (the folder above it), $MULTIVERSECTL_ROOT or --yes settle it without asking, and a --root that already holds the checkouts reuses them. The first project installed becomes the current one. A source is read as a node in your catalog, then a path, then a git URL, then owner/repo.

Keep installed projects current

$ multiversectl project status --fetch
PROJECT    FROM            STATE
* acme      acme/multiverse  manifest behind 1 · billing-api not cloned
› next: multiversectl project update acme
$ multiversectl project update
✓ billing-api: cloned
✓ acme: manifest moved forward 1 · billing-api cloned

status compares each project with where it came from, offline unless you pass --fetch. update fetches, moves each manifest forward and clones what the new one lists; it refuses a manifest with local changes and leaves a pinned one alone. uninstall <name> forgets a project and leaves its files.

Hearing about changes while you work

Nothing updates by itself; you are told. Every command under universe opens with a line when the manifest has moved upstream, as do status and project status. To have that news be current, a command looks at the remote when the last look is over six hours old, for at most four seconds, silently if it fails. MULTIVERSECTL_NO_FETCH=1 turns it off.

$ multiversectl universe ls
! acme: 2 upstream changes to its manifest: multiversectl project update acme

Editing the manifest here

A manifest installed from a repository is a checkout under <root>/.multiverse/workspace. Edit it there and keep working: update never overwrites an edit, and status says what it found.

  • Edited, nothing upstream: manifest edited here. A choice, not news.
  • Edited, and upstream moved: manifest edited here · manifest behind 2 — keep working, or stash, update, git stash pop.
  • Committed here, and upstream moved: manifest diverged (1 local, 2 upstream). update cannot fast-forward; git pull --rebase in that folder.

A project installed from a file has nothing to compare with and is never updated.

Make a project others can join

# in an empty directory, or a checkout of the repository you made for it
$ multiversectl project init

The guide asks in turn and shows the plan before creating or pushing anything:

  • Its repositories. The checkouts already beside the directory (each origin becomes its URL), a search through your repositories on GitHub or GitLab, or URLs you paste. Mix them as you like.
  • Its name. What most repository names start with — acme-api and acme-ui make acme, and shorten their keys to api and ui.
  • Where its own repository lives. A new private one under any account you can create in, one that exists, the directory's own origin, or only this machine.
  • Where to list it in your root catalog, and whether to install it here so the next command can be universe new 1.

It writes multiverse.yaml, catalog.yaml and a short AGENTS.md, commits and pushes. That AGENTS.md tells a person or a coding agent what the repository is and how to run universes of it; one already there is left alone. A repository with a docker-compose.yml becomes an app of the same name, and one found cloned without one is marked runtime: none. GitHub needs gh and GitLab needs glab; choosing a service you are not signed in to signs you in first. Any other host works by URL. Every answer has a flag, so with enough of them it asks nothing:

$ multiversectl project init ~/acme/multiverse --scan --create acme-org/multiverse --yes
$ multiversectl project init --name acme --repo acme-org/api --repo https://gitlab.com/acme/web.git --local

What it makes is a project repository: one repository that is both the catalog listing the project and the home of its multiverse.yaml. The entry carries no repo, because a reference stays in the repository it is written in.

# catalog.yaml in acme-org/multiverse
apiVersion: multiverse/v1alpha1
kind: Catalog
metadata:
  name: acme
spec:
  projects:
    - name: acme
      source: {path: multiverse.yaml}   # this repository's own manifest

Anyone else then runs multiversectl project install acme-org/multiverse. Writing those two files by hand does the same. Leave machine-specific lines such as an absolute spec.root out of a manifest you share: install picks where it goes.

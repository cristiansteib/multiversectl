Control which services run

Start optional services on demand, keep a published port, and give a service its own hostname.

Let a service declare its own hostname

Put a label on the service in its own compose file: the key names the host, the value is the container port.

services:
  app-dev:
    labels:
      dev.multiversectl.host.app: "4200"   # app-u3.<domain> -> port 4200

With no labels at all, a service exposing exactly one port is already reached at the app's own name. See Labels and variables for entrypoints and aliases.

Keep a service's published port

Universes drop every published host port, so two copies never collide. A service that genuinely needs one asks to keep it:

services:
  db:
    ports: ["5432:5432"]
    labels:
      dev.multiversectl.publish: "true"

Or, without touching the repository, publish: [db] on the app in the manifest. Only one universe can hold that port at a time.

Choose where exec and run go

An app with several services makes universe exec and universe run ask for --service every time. Name the one you almost always want:

# multiverse.yaml, on the app
defaultService: web

--service still wins. When the app lists services, the default must be one of them.

Run your own tools at the points of a universe's life

A universe that is up is not always one a person can use: a fresh database has no user to log in with, and an identity provider does not know the address the universe answers on. multiversectl does not know about either. It gives a project one thing, a command tied to a point in a universe's life, run in a container or on the machine, and tells it where the universe is. What the command does is the project's.

# .multiverse.yaml, on the app
hooks:
  preUp:
    - name: let the build read the netrc
      host: {command: [./scripts/prepare.sh], dir: api}
  postUp:
    - once: true
      container:
        service: web
        command: [python, manage.py, createfixture]
    - host:
        command: [sh, -c, 'curl -fsS -X POST "$AUTH_URL/clients/frontend/redirects" -d "uri=$WEB_URL/*"']
      retryFor: 2m

Events

EventWhenRuns
postCreatethe universe's worktrees exist; nothing has startedon the machine
preUpbefore the app is built and startedon the machine
postUpthe app's services are upin a service, or on the machine
preDownbefore the app is stoppedin a service, or on the machine
postDownthe app is stoppedon the machine
preRemovebefore the universe is destroyedon the machine

spec.hooks takes the same events for the multiverse as a whole, on the machine: postUp there runs once every app is up, which is where an address that all of them share is registered. after is the earlier name of postUp.

What a command is told

The environment has what a compose file already gets (UNIVERSE, UNIVERSE_DIR, MULTIVERSE_DOMAIN, and <HOST>_URL for every address), plus <HOST>_FORWARD_URL for one that is also reachable by IP and port, MULTIVERSE_EVENT and MULTIVERSE_APP. A command on the machine also gets MULTIVERSE_CONTEXT_FILE: a JSON file with the same and more (every address with its service and port, each repository's directory, the branches), for a script that wants to build an .env or a redirect URI from it. The file is removed afterwards. There is no shell: say sh -c when one is wanted.

A hook that only writes a file from these values, a config or an .env, is what render is for: no script, and it is written before the app starts, kept out of git's sight, and only rewritten when it changes.

When it does not succeed

A command in a service after the app is up is tried again for a few minutes, because the service may still be starting (a database migrating under it); retryFor asks any command to be, and timeout ends a try that hangs. onFailure says what a failure means: warn says so, with how to run it by hand, and goes on, the hooks after it waiting since they may depend on it, and it is tried again next time; fail ends the command with an error; ignore goes on. A preUp fails by default, since what it prepares is what the start needs; the rest warn, so a hook that breaks cannot keep a universe from being stopped or removed. once runs a hook on the first start of each universe only; without it a hook runs every time, so it should be safe to repeat. service can be left out when the app has one service or a defaultService.

See them, and run one now

multiversectl universe hooks 3 lists a universe's hooks with where each runs and whether a once-only one has run. universe hooks run 3 postUp api runs an event's hooks now, for one app or (with none named) the multiverse's and every app's: how a hook that was warned about is run again, and how one is tried before it is trusted to a start. A failure there is an error whatever onFailure says.

Write a config file from the universe's addresses

Many apps read a file at startup, a JSON or YAML config, a .env, a framework's settings, and cannot take environment variables. A hook can write that file, but every project then carries its own inline script. render is the declarative form: a template, a path, and the universe's values.

# multiverse.yaml, or .multiverse.yaml on the app
render:
  - to: public/config.json
    mode: "0600"
    template: |
      {
        "apiUrl": {{ url "api" | toJson }},
        "callback": {{ forward "api" | toJson }},
        "allowedOrigins": {{ .Origins | toJson }},
        "universe": {{ .Universe | toJson }}
      }
  - to: .env.universe
    from: "@templates/env.tmpl"   # next to the manifest; a plain path is in the repository

Each entry has to, a path inside the app's repository checkout in the universe (it cannot leave it, and git's own directory is refused), and either template or from. A from without a prefix is relative to the checkout; one starting with @ is relative to the manifest's directory, as compose is. mode is the permission, 0644 unless said.

When it runs

On every universe up, for each app being started, before its compose files are read and before anything starts, so the file is there when the service boots. It is not run by universe new: a forwarded address is chosen at the first start, and a template that needs it would fail before it exists. A file is written only when its content (or permission) changed, through a temporary file and a rename, so a file watcher is not retriggered and a service never reads half a file. up prints a line per file, rendered or up to date.

What it does to git

The file lives in the worktree. Its path is added once to the checkout's exclude file (git rev-parse --git-path info/exclude), so it does not show as an untracked change, and the repository's tracked .gitignore is not touched. For a universe, which is a linked worktree, git keeps that file with the clone, so the entry is shared by the clone and every universe of it; it is anchored, so it matches that one path. An entry whose file git tracks is an error, so a template cannot overwrite source; overwrite: true allows it, and the change then shows in git status like any other. A path that would, through a symbolic link, be written outside the checkout is refused too.

What a template can read

Go text/template syntax, with a missing key an error rather than an empty string.

NameValue
.Universe, .Slug, .Number, .DomainThe universe's name, the slug its hostnames carry, its number (0 for a named one), and its domain.
.App, .Dir, .RepoDirThe app, the universe's directory, and the app's checkout.
.Hosts, .OriginsEvery hostname, and every address as an origin (hostnames first, then the forwarded http://<ip>:<port> ones), as lists in a stable order. .Hosts has names only.
.EnvThe environment a hook receives: <HOST>_URL, <HOST>_FORWARD_URL, UNIVERSE, the manifest's own env, and so on.
host "k", url "k", forward "k"What the labels host:k, url:k and forward:k give: the hostname, the address with its port, and the address by IP and port (an error for a host with no portForward, or before the first start).
origins, hostsThe labels' origins and hosts joined; give "comma" (the default), "space", "semicolon" or "newline": {{ origins "space" }}.
env "NAME"A variable of .Env; an error when it is not set.
default fallback valueThe fallback when the value is empty: {{ index .Env "TOKEN" | default "none" }}.
required "message" valueAn error with that message when the value is empty.
toJson valueThe value as compact JSON, quoted and escaped, which is what a string in a JSON file needs.

An error names the app, the file and the key, and stops the start: api: render public/config.json: template: public/config.json:2:14: executing "public/config.json" at <url "billing">: error calling url: no host "billing" in this multiverse (have: api, web).

See it, and run it now

multiversectl universe render 3 renders a universe's files now, for the apps named or all of them, from the addresses it last started with. --print shows the result and writes nothing, which is how a template is tried.

Start the dev service and not the production one

A compose file often defines the same app twice, a dev server and a production build, and both start by default. Say which, in the manifest, without touching the repository:

# multiverse.yaml, on the app
services: [app-dev, api]          # only these start
# or, if the compose file marks the extra ones with profiles:
profiles: [dev]                   # always on, as --profile dev

Only the services that start are given an address and lose their published ports; the others are never created. optional adds groups on demand with --with.

Build with a secret file, such as ~/.netrc

Recent buildx refuses a build whose secrets: file: lives outside the project (~/.netrc) unless it is allowed. The tool does not decide that for you; spec.env reaches every compose and build call, so the project says it once:

# multiverse.yaml
env:
  - name: BUILDX_BAKE_ENTITLEMENTS_FS
    value: "0"

Anything else a build needs from the machine is the same: an environment variable in spec.env, or a preUp hook that prepares it.

Run optional services on demand

# multiverse.yaml, on the app
optional:
  - name: celery
    services: [worker, beat]
$ multiversectl universe up 3 api --with celery

The group name is activated as a compose profile too. Comma-separate several: --with celery,mail.

Keep an app from starting by default

An app that should exist in every universe but not run unless someone wants it — a tool that needs extra setup, a code generator, a heavy optional service — says so:

# multiverse.yaml, or the repository's own .multiverse.yaml
apps:
  - name: codegen
    autostart: false
$ multiversectl universe up 3              # every app but codegen
$ multiversectl universe up 3 codegen      # starts it

An app with autostart: false is still checked out and has its addresses, so others can refer to it and starting it later needs nothing more. A start that names no app prints one line for each one it leaves out. down, rm and hooks run with no app named deal with it only while it is running; doctor and ls show it as off, on demand, not as a failure. Unlike optional, which adds services to an app that already starts, this decides whether the app starts at all; --with does not start it.

Configure what depends on the universe

A universe's hostnames do not exist until it does, so anything built from them — trusted origins, allowed hosts, CORS, a front-end's API base URL — is asked for with a label on the service that needs it:

services:
  web:
    labels:
      dev.multiversectl.env.DJANGO_ALLOWED_HOSTS: hosts
      dev.multiversectl.env.DJANGO_CSRF_TRUSTED_ORIGINS: origins
      dev.multiversectl.env.API_BASE_URL: url:devapi

These win over the service's own environment: and over any env_file:, which is how a static list in a committed .env stops being what the universe runs with. The sources, and why it is a label rather than a variable reference, are in Labels and variables. For a repository you cannot change, the app's inline overlay: does the same from the manifest:

apps:
  - name: api
    repo: api
    overlay:
      services:
        web:
          environment:
            DJANGO_CSRF_TRUSTED_ORIGINS: "${MULTIVERSE_ORIGINS}"
            DJANGO_ALLOWED_HOSTS: "${MULTIVERSE_HOSTS}"

When the app reads a file and not its environment, render writes that file from the same values.

multiversectl universe env <universe> prints every variable a universe passes.
